## 结论（行号与计数由本脚本从上面各命令的捕获输出机械提取，非手写）

- Command 1：生产源码里 `BranchSource.restore` 共 2 行命中，且全部落在同一个文件 `BranchDao.java` 内。
  其中 1 行是注释里的文字引用（`BranchDao.java:228`，解释为什么空快照要在这里先判），
  1 行是真实调用（`BranchDao.java:239`）。
  因此「`:data` 生产源码中 `BranchSource.restore` 恰好 1 处调用」成立；该调用点就在
  `BranchDao` 内，且同一文件里与它相邻的注释行 `BranchDao.java:228` 正是 `readSource` 的空快照前置判，
  故限定词「位于只读映射（read path）内」与命中位置一致。
- Command 2：井号写法命中 3 行；其中 `:core` 的 `AnswerRevision.java:112` 是 javadoc 交叉引用，
  提醒这条断言的范围必须限定在 `:data` 生产源码，而不是「全仓零命中」。
- Command 3：把范围放宽到整个 `android/` 后共 12 行命中 —— `:core` 的 `BranchSource.java:94` 是定义本身，
  其余分布在 `:core` 测试与 `:app` 测试。这正是任务文件在验收条件 7 上加了限定词的依据。
  与本任务修复直接相关的一项：androidTest 侧的真实调用（`BranchSource.restore(`）为 0 处，
  与本任务把创建用法改走真实创建入口 `BranchSource.fromOperation(..., GenerationState.STABLE, ...)` 相符。
- Command 4：`Branch.restore`（`BranchDao.java:175`）与 `Message.restore`（`MessageDao.java:85`）各自只出现在
  所属 DAO 的只读映射内；`TreeLearnSchema.java:330` 是注释里提到 `AnswerRevision.restore` 的文字，不是调用。
- Command 5：捕获输出为空、按输出行数计 0 行，即零匹配；EXITCODE=1 表示「没有匹配」（grep 以 1
  表示无匹配，不是执行失败）。这一条由「输出段是否为空」直接读出，不靠退出码反推。
- Command 6：对照命令 —— 全 `:data` 生产源码里含 DDL 关键字的文件共 1 个（TreeLearnSchema.java），
  EXITCODE=0 且匹配集非空。Command 5 + Command 6 共同支持 android/README.md 中「DDL 单产地」的声明。
  上一版证据在此处的结论行与自身输出相矛盾（输出有匹配却写着 no output），本次改为对输出的直接陈述。
