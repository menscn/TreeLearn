一、缺陷定位：先分清是 alpha、是几何、还是投影
-------------------------------------------------
home_appbar 在 dumpsys 里是 52,20-1148,189（窗口坐标，绝对 y=135..304）。它自己的控件只占两段：
抽屉钮 x=78..195、设置钮 x=1005..1122。所以 x=200..1000 这一段在 y=140..302 里出现的任何墨，
只可能来自栏下穿过的内容——这就是取样框的选法，不需要猜。

三条候选原因分别量：

1. 左右裸条（x<52 / x>1148，栏没盖住的地方）：
   两帧同位 |ΔL| = 0.00，L 稳定在 238（左）/ 232（右），是雾面背景本身。
   结论：**没有内容从栏外侧穿过**，`home_content` 与 appbar 同为 52..1148 内缩，几何不是缺陷。

2. 胶囊投影带（圆角弧之外）：
   修前有 48 个强变化点落在 x=62..80 / y=261..286，修后剩 20 个、挪到 x=1120..1136 / y=276..283。
   这一族 075 已经登记过（那次是 48 点 / 0.09%）。它不是文字，是投影与圆角弧的接缝，本片不动它。

3. 面内透印（x=200..1000）：
   见第 2 节。这才是用户报的那件事。

第一次取帧时踩到一个坑，如实记下：`adb shell input swipe 600 1600 600 700 420` 这一条**没有让页面
滚动**（正文中段/下段两帧同位变化 0.00%），所以那一对帧读出来的「栏带有 5% 在动」全部来自投影带，
不是透印。改用 `swipe 600 600 600 2200` 连四下回顶 + `swipe 600 1900 600 500 300` 下滑之后，
正文三段变化 44.20% / 51.23% / 45.43%，栏带 4.15%——这才是一对真在滚的帧。
判据脚本要求的是「两帧必须不同位」，取错帧会让 FAIL 长得像 PASS。


二、判据：8 L 这条线不是本片新调的数
-------------------------------------
`check_glass_depth.py` 里 `J4_MIN_DRIFT = 8.0`，注释写的是「滚动时玻璃覆盖行的亮度变化至少 8」，
它的自检还反向断言「同一张图两次必须读不出漂移」（`drift < 8`）。也就是说 8 L 是本项目**已经登记**
的「看得出来面下有东西在动」的分界。

对通透面（chrome），越过 8 L 是拿分；对控制面，同一把尺是**上限**——072 给这一面的定义就是
「面上的文字压在别处文字之上，判据是读不读得清」。所以本片的判据写成：

    胶囊面内中段（x=200..1000）推荐语穿过的那几条行，两帧同位 |ΔL| max 必须 < 8.0 L。

复现：python -X utf8 artifacts/evidence/topbar-ghost-2026-10-23/077-bar-ghost.py


三、读数
---------
修前 --glass-control rgba(255,255,255,.93)：
      y=256..284  变化像素 13.62..22.25%   |dL| P95 9.28..10.21   max 10.28   -> 8 条行全 FAIL
修后 --glass-control rgba(255,255,255,.98)：
      y=256..284  变化像素 0.00%           |dL| P95 3.00          max 3.00    -> 8 条行全 PASS

单帧墨深（同一批行，面内 P01 与中位的差）：11.28 L -> 3.00 L。
这条比例就是 alpha 的算术：11.28 x (1-.98)/(1-.9294) = 3.19，实测 3.00，对得上。

把取样从「穿过的那 8 条行」扩到**整张面内**（x=200..1000 step2，y=140..300 step2，共 32400 个采样点，
两帧同位）：
      修前 .93：|dL| max 10.28，越过 8 L 线的像素 974 / 32400 = 3.01%
      修后 .98：|dL| max  3.00，越过 8 L 线的像素   0 / 32400 = 0.00%
这条比 8 条行的结论更强：面上没有任何一处以 8 L 的幅度把下层带上来，不只是那几条推荐语。

对照 Web 同位（075 留下的读数，本片 Web 零改动）：变化像素 0.00% / |dL| 最大 2.28。
修后 Android 3.00 L，与 Web 的 2.28 同档，仍在 8 L 线内。

对照图 `077-bar-frames.png`（生成脚本 `077-frames.py`，同目录）取的是**面内** y=130..306，
四格分别是修前 A/B、修后 A/B。为什么放四格而不是前后各一张：推荐语自己就在轮播，
「修前 frame A vs 修后 frame A」这一对里那一行根本不在同一位置，拿它当证据会把轮播当成缺陷。
真正可比的是 B vs B（同一滚动位、同一行墨）：修前那一行整条印在面上，修后只剩 3 L 的水印。
A 两格保留着，是为了让人看出「在顶部时这一面本来就干净」——缺陷只在内容穿过栏下时出现。

底部胶囊（tab_bar_pill，同一枚面）：本片没为它重测——它的面内中段在这两帧里变化 0.00%，
因为那两条帧里恰好是列表底部留白经过；072 当时量它是因为标签与列表文字**同时**在胶囊内。
alpha 只朝「更遮住」的方向动，这一面不会因本片变差。

五、覆盖面缺口（如实记下）
---------------------------
1. 只有手机真机，没有宽窗/Pad 截图。layout-sw600dp 的两份栏同样吃 `bg_glass_control_bar`，
   alpha 是共享的，所以材质结论可迁移；但「宽窗下推荐语穿过常驻栏」这件事没在宽窗上实拍过。
2. 库页（library_appbar）同一枚面、同一条链，本片没重测。075 量过它：顶栏带 0.83% / 中位 0.07，
   栏内本来就没有常驻动画，alpha 只朝更遮住的方向动。
3. 修后 3.00 L 是「水印」而不是「可读文字」，但**不是零**：把图放大到 2x 仍能在栏内看出那一行的影子。
   如果下一轮用户还说看到重叠，可用的杠杆是 .99（算术预测 1.5 L，优于 Web 的 2.28），
   代价是这一面在静态下与纯白只差 0.3 L，玻璃身份只剩 sheen / 边线 / 圆角 / 投影在承担。
4. Android 没有真背景模糊，这条端差是 075 登记的，本片没有推翻它，只是把 alpha 抬到
   「不需要模糊也读不出下面」的那一档。RenderEffect 只能糊视图自身，糊不到 backdrop，
   所以这条路在 Java-only 上走不通；真要拿回「透而不可读」，得走 PixelCopy 截栏后区域再糊，
   那是另一片的量级，本片没做。
