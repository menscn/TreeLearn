## 结论（计数与判定由本脚本从上面各命令的捕获输出机械提取，非手写）

- Command 1：持久化层 `:data` 生产源码 零命中 —— `systemContent`/`systemPrompt`/`promptBody`
  形态的标识符一个也没有。这是断言「本任务所有 DAO 的公开方法签名中不出现此类入参」的正面证据。
- Command 2（对照，刻意保留）：同一检索放宽到 `:core` 后 命中 8 行，位于 PromptSpec.java。
  这不是本任务的违规，而是这条断言的**边界**：`PromptSpec` 是 T-021 的**内存态请求装配体**
  （purpose + version + 正文），正文在设计上只存在于内存与 `:ai` 的注册表里，从不落库 ——
  `PromptPurpose` 的 javadoc 与 `TreeLearnSchema` 的列清单都写了这一点。把它如实记下来，是为了让读者
  不会用一条全仓检索去「证明」一个只对持久化层成立的断言（本仓库已经因为把搜索范围写错而误报过）。
- Command 3：`PromptSpec` 在 `:data` 生产源码里 零命中，即携带正文的类型没有进入持久化层。
- Command 4：本任务新增类的公开/静态签名共 28 行；其中入参为标识符的签名 11 处，
  入参含 content/body 形态的签名 0 处。其余入参是 `delta`（模型输出增量）、`state`、
  `terminal`、`errorCode`、`now`、实体对象或 `SQLiteDatabase` —— 没有任何方法可以接收一段 system prompt。
- Command 5：新增类内与提示词相关的命中 12 行，其中引用列常量 6 处，全部指向
  `prompt_purpose` 与 `prompt_policy_version` 两列；没有任何一处把正文写进列。
- Command 6：表结构侧的既有守门仍在（命中 1 处），它断言七表里只有 `prompt_purpose` 与
  `prompt_policy_version` 两列与提示词相关，且没有任何列名含 `system`。
- Command 7：行为侧哨兵用例存在（命中 1 处），它在真机上扫描两表全部 TEXT 列。
  证据强度已在用例 javadoc 中如实标注：purpose/version 两条断言有实质内容（写成正文或写成未经注册的版本都会失败），
  哨兵扫描是**绊线**而非证明 —— 本任务的写路径根本不接受正文，因此它防的是未来新增的列或 DAO。
