一、为什么这次要先把曲线量出来（用户拍板「玻璃的不透明度太低了」）
顶栏是 Web 上唯一的覆盖层，「内容穿过玻璃」的像素信号与顶栏 alpha 是同一根轴：alpha 越高，
穿过来的内容越淡。这条轴不是推定，是运行时单变量实测（artifacts/tmp/opacity_sweep.mjs 与
opacity_sweep2.mjs，仓库文件未改，618×1350 聊天帧顶栏同一面框 61,1..1175,127）：
  chrome .54（现状）→ J4 11.3 L
  chrome .58 → 9.9 L      chrome .62 → 8.3 L      chrome .66 → 7.1 L
  chrome .70 → 5.9 L      chrome .74 → 4.9 L      chrome .78 → 3.9 L
  chrome .70 + falloff .45 → 6.1 L（把 tint 暗端调回 .31 alpha 只换回 0.2 L：
    支配项是整面 alpha，不是 145° 暗端，所以「上实下透」救不回这条信号）
阈值 8.0 L 之下的天花板是 chrome ≈ .62。用户在这条曲线上的裁决（2026-10-23）：
「跟到 .74，放弃 Web 的像素判据」——顶栏与其余四面一起变实，Web 顶栏不再主张 J4，
让位结构改由 CSS 断言兜住；Android 的 J4 主张保留。

五、机械断言（不依赖取景的两端下限）
Web：`frontend/test/styles/glass.test.ts`「五面 alpha 停在拍板下限之上」——读生成的 tokens.css，
chrome/card/reader/field 下限 .70/.84/.92/.70。RED：`expected 0.54 to be greater than or equal to 0.7`。
Android：`GlassMaterialTokensTest.theGlassSurfacesStayAboveTheAgreedOpacityFloors`——读 tokens.json 同一组下限。
RED：`glass-chrome must stay at or above alpha 0.7, got 0.54`。
下限而不是当前值：把 token 抄进测试会出现第二份事实，且它对「更透明」这个方向永远不响。
