**CHECK 约束的「标识文案」本身随 SQLite/Android 版本变化**，而旧 `assertCause` 的第二半
（`requiredText`）恰好断言的就是这段文案：
  | 环境 | 同一次 CHECK 拒绝的文案 |
  | :--- | :--- |
  | API 36 模拟器 | `CHECK constraint failed: role IN ('USER','AI')`（**表达式**） |
  | Android 13 真机 | `CHECK constraint failed: messages` / `CHECK constraint failed: branches`（**表名**） |
两种文案**没有任何共同片段**。裁定采用**两段式证明（三角证明）**：运行时断言「码 = 275 且拒绝
来自该表」、静态断言「`sqlite_master` 的 DDL 声明了该约束的期望片段」、同一测试内补**正控**
（合法行必须被接受）；否决「按已知拼写二选一」，延后「给 CHECK 约束起名」（越过本片红线）。
残余损失如实登记：运行时文案不再能证明「是该表上的哪一条 CHECK 拒绝的」。

## 9. CHECK 约束的标识文案（2026-09-22 已裁定：采用两段式证明）

# 裁定记录（正文以任务文件为准）：
#   .trae/tasks/T-2026-09-22-constraint-codes-and-red-suites-060.md
#     「## Implementation notes」→「### CHECK 标识文案的裁定（2026-09-22，leader 裁定…）」
#   裁定要点：
#     * 运行时 —— 断言「扩展码 = 275 且 拒绝来自该表（messages / branches）」；
#     * 静态   —— 断言 sqlite_master 的 DDL 声明了该约束的期望片段；
#     * 正控   —— 同一测试内必须断言合法行被接受；
#     * 三段合起来是「声明存在 → 该表发生 CHECK 拒绝 → 合法行通过」的三角证明。
#     * 否决 A（按已知拼写二选一，表达式 或 表名）：那是 || 条件的并集，判别力更弱，
#       而且把版本差异写进断言，下一轮 Android 再改文案时还会漂。
#     * 延后 C（给 CHECK 约束起名 CONSTRAINT ck_...）：唯一能恢复「精确到该约束」且
#       版本无关的结构解，但改 CREATE TABLE DDL、既有库还需重建表，越过本片红线，
#       记为独立片候选，须由用户另行授权；本片不做。
#   残余损失（必须如实登记，不得写成「精确到该约束」）：运行时文案不再能证明
#   「是该表上的哪一条 CHECK 拒绝的」，这部分由上述三角证明承担，不由文案承担。
#   三角证明三段的落地证据见第 10、11、12 节。
#
# 以下 A/B/C 三选项与事实枚举是本片裁定前的原始分析，保留作为这次裁定的依据。

### 9.1 事实（裁定前记录）
* 真机 4 个失败全部是 `assertCause` 的第二半（`requiredText`）不满足，而不是码值那半：
  `the failure must name <表达式片段> but was CHECK constraint failed: <表名>`。
* 同一次失败在 API 36 上文案是**表达式**（`role IN ('USER','AI')`，见
  artifacts/evidence/T-004-constraint-code-probe.txt 的实测行），在 Android 13 上是**表名**
  （`messages` / `branches`，见第 3 节真机日志）。
* 两种文案**无共同片段**：`anchor_start_inclusive` / `last_seen_stable_sequence` / `role = 'AI'` /
  `source_message_id IS NOT NULL` 都只出现在 API 36 那一侧；`branches` / `messages` 只出现在
  Android 13 那一侧（API 36 的文案里不含表名）。
* 受影响的断言共 13 条、分布在 4 个测试方法（第 3 节枚举）。这些断言在作业单的 26 个失败里
  只贡献了 4 个「方法级」失败，且当时**卡在更早的码值断言上**，所以这段文案依赖从未被看见——
  本片修好码值那半后它才露出来。
* CHECK 的这两半都不能靠现有信息替代：对 `messages` 的未知 role 插入，role CHECK 与两条内容
  CHECK 会**同时**违反（`role='ROBOT'` 无论 content 是否为 NULL，都至少违反两条），所以
  「哪条 CHECK 拒绝的」在 Android 13 上**无法从文案判定**；`branches` 上同理（锚点 CHECK 与
  来源 CHECK 都可能命中）。这也是为什么原套件坚持用文案而不是靠 DDL 声明顺序。

### 9.2 三个选项（都需要作者裁定，因为它们都改变断言的形状）
A. **测试侧接受「两种实测拼写之一」**：`assertCause` 对 CHECK 类允许「命名了表达式片段」**或**
   「命名了该表」。代价：具体到哪条 CHECK 的判定退化为「该表上的 CHECK」。
B. **测试侧改为断言 DDL 声明了该约束**：保留「码值 275 + 该表」，把「具体是哪条约束」改为断言
   `sqlite_master` 的 DDL 里含期望片段（套件已有 `tableDdl/schemaObjectDdl` 读法）。代价：断言
   从「拒绝来自这条 CHECK」变成「DDL 声明了这条 CHECK + 该表发生了 CHECK 拒绝」，属推断而非直接证据。
C. **生产侧给 CHECK 约束起名**（`CONSTRAINT ck_... CHECK (...)`）：命名约束在**所有**版本上都
   报 DDL 自己的名字，才能恢复「精确到哪条约束」的版本无关判据，并让这类漂移结构上不可能再发生。
   代价：属 schema DDL 变更（且 SQLite 不能 ALTER 一个 CHECK，老库需要重建表迁移），
   超出本片「不得改 schema / migration」的红线，需要另立一片。

### 9.3 建议
以 **A** 作为本片的立即解封（改动小、只在测试侧、且保留了「该环境能给出的最强判据」），
把 **C** 作为后续独立片的候选（若审查认为「精确到哪条 CHECK」必须保留，则只有 C 能做到版本无关）。
无论选哪一条，`ConstraintFailures.isUniqueOn` 的「码值 + 列名列表」双重判据都不受影响——
它判的是 UNIQUE，而 UNIQUE 的文案在两种环境上实测一致（真机日志里 `messages.branch_id,
messages.ordinal`、`branches.topic_id`、`generation_operations.branch_id` 等断言全部通过）。
