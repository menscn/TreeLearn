## 10. GREEN 期间的两处中途修正（诚实记录，都不改断言）

1. 测试驱动自身的缺陷：assertHighlighted -> labelColor/iconTint 里把 view(id)（内含 runOnMainSync）
   写进了另一个 runOnMainSync 里，平台直接抛
   `RuntimeException: This method can not be called from the main application thread`，
   3 个用例在断言前就崩。改为在已经处于主线程的 lambda 里直接 activity.findViewById。
   -> 这是测试代码的缺陷，不是产品行为，且 RED 阶段从未执行到这一行（RED 停在编译期）。
2. 产品侧的真实缺陷（由本片这条新验收路径第一次走出来的）：
   MainActivity.render(ChatViewState) 原先无守卫，showChat 之后被二级屏接管时 chatScreen 已置空，
   而对话屏的读（以及生成中的轮询）仍会晚到 -> NPE on null，
   `at com.treelearn.app.MainActivity.render(MainActivity.java:295)`，
   进程崩溃并让本轮 5 个用例只跑到 3 个。
   修法：render(ChatViewState) 与 renderPosition(ReadingPosition) 加与既有导航页同款的 null 守卫
   （只加不删、不改语义、屏幕为空时只是丢弃这一帧），并把导航页那段「只有它会晚到」的注释同步为事实。
   -> 这是既有缺陷被新流程暴露，不是本片引入的回归。
3. 设备在睡（见第 5 节）与一次 `dexBuilderDebug ... graph.bin (拒绝访问)` 的 Windows 文件锁抖动（重跑即过）。
