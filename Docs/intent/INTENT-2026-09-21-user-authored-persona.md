## Problem（问题与背景）

- 诉求：用户可创建自己的人设，**自己输入对应的提示词文本**，AI 回答时参考它。
- 与内置人设的关系：内置人设是先行的一期，已 `accepted`，见 `Docs/intent/INTENT-2026-09-21-ai-persona-preference.md`。本文件只承载**后置的自建层**；两文件共享的已确认事实（作用域跟着主题走、不影响派生输出、最高规则不可解除）不在此重复。
- 不做的后果：内置层已接受的那三条（回答太水学不到东西、被迫每次手写风格要求、手写要求污染主线）**同样适用于本层**——手写要求正是自建人设要替代的动作。但本层**独有**的价值主张（覆盖内置 7 档之外的领域身份）目前只有推测，没有具体场景。

### 已核实：本层与七处冻结边界正面冲突

| # | 权威位置 | 原文要点 | 冲突点 |
| :--- | :--- | :--- | :--- |
| 1 | V3.1 §三 共同约束末条 | 系统提示词由应用内版本化注册表维护，**首版不向用户开放编辑** | 用户自建即是编辑提示词正文 |
| 2 | V3.1 BASE-26 | **不得在提示词中插入用户正文** | 用户文本要进提示词 |
| 3 | V3.1 BASE-26 | 不得借上下文文字改变 system 角色 | 若改走 user 角色消息注入，正是这条要防的形态 |
| 4 | 架构方案第 63 行 | `:ai` **不接受用户自定义 system 模板** | 自定义模板 |
| 5 | 提示词设计第 51 行 | 注册表只接受枚举，**不接受用户提供的模板名、系统提示词或任意插值** | 用户文本就是插值 |
| 6 | 建表规则第 44、45 行 | **No column may hold the system prompt body** | 用户人设正文没有任何列可以存放 |
| 7 | 提示词设计 §3.2 版本规则 | 每个不可变生成命令固定版本，创建回答记录时原样复制 | 用户可改的文本没有稳定的版本身份 |

- 好消息：**内置层已经铺好一半机制**。`AnswerRevisions.THINKING_ENABLED` 那种「不影响提示词版本的身份列」形态已在生产运行；自建层要新增的是「用户内容 + 不可变版本 + 回答引用其版本快照」，与本仓既有的「子分支固定出生快照」同构。
- 边界修订授权：用户已明确「暂时不限制改」，对上表七处的修订不再受「已冻结」限制，作为本需求的一部分统一执行。

## Users and scenarios（用户与场景）

- 谁：单人自用，只有用户本人。
- 场景（**假设，未证实**）：内置 7 档覆盖不到的领域身份，例如「面试官」「论文评审」；或者只想微调内置某一档的措辞。
- 作用域：沿用内置层的决定——**跟着主题走**。

## Expected outcome（预期结果）

- 用户能写一段自己的风格要求，并在主题里选用它，AI 回答时参考它。
- 用户文本**不得**解除最高规则。用户已给判例：要求「不要纠正我的错误前提」的人设，AI 不照做。
- 旧回答的复现口径明确：引用当时那一版人设的快照，还是当前文本。

## Core flow（核心流程）

- 核心流程（含中断、撤销、重试）：**待收敛**。
- 输入/输出：用户输入一段提示词文本；产出物形态（是否版本化、能否多次编辑、编辑后旧版本是否保留）**待定**。
- 状态与异常：**待定**。
- 删除与失效：用户修改或删除自建人设后，引用它的旧回答读到什么？**未知项**。
- 入口：内置层已确认需要一个**人设介绍页**，该页作为自建层的承载位置，本期只预留位置、不实现。

## Constraints and non-goals（约束与非目标）

- 约束：
  - 用户文本只能作用于风格、深度、节奏与措辞，**不得触及事实准确性、纠错义务与不得编造**（最高规则）。
  - 用户文本不得成为不可版本化的隐式状态：必须能确定「这条回答当时用的是哪一版人设」。
  - 沿用内置层：system 消息恰好一条且位于第一位；日志、测试报告与遥测不得记录提示词正文；Java-only。
- 权衡偏好：**待用户拍板**——用户文本的自由度，与「可复现、基线不可解除」之间。
- 非目标（non-goals）：
  - 本期不做，自建层后置。
  - 不允许自建人设解除最高规则。
  - 不新增服务端、账号、同步；不引入非 DeepSeek 供应商。

## Open questions（开放问题）

- 已确认事实：
  - 形态：用户自建人设并输入提示词文本。
  - 最高规则不可解除（判例：不纠正错误前提的人设不照做）。
  - 边界修订已获用户授权。
  - 作用域跟着主题走；不影响标题、分支摘要、推荐问题等派生输出。
- 假设（未证实，不得升级为事实）：
  - 用户存在内置 7 档覆盖不到的领域身份需求。
- 未知项（**必须由用户回答或明确授权后由我提出方案，不得代填**）：
  1. **不可解除的验证方式**：怎么机械验证「用户文本没能解除最高规则」。用户已决定**留到设计阶段解决**。在这一条解决前，本层无法写成「命令 + 期望输出」的验收。
  2. 自建人设的持久化形态：是否需要新增用户内容实体与不可变版本；正文存在哪里（建表规则目前禁止任何列存放 system 正文）。
  3. 自建人设被修改或删除后，旧回答读到的是当时的版本快照还是当前文本。
  4. 自建人设的数量上限与文本字数上限，一律留空待定。
  5. 自建人设是否也必须能被归类到内置的那 6 根轴（即可验收），还是允许纯自由文本。
  6. 介绍页里自建部分的形态，本期只预留位置，具体待定。

### 值得做吗

结论：需要更多信息
证据：它是内置层的自然延伸，用户也已定分期（内置先行）。但成本明显高于内置层——需要新增用户内容实体、改变「提示词正文不入库」的建表规则，并重新定义可复现口径。

### 可以做吗

结论：需要更多信息
证据：形态已由最高规则确定（受基线包住的风格层 + 不可变版本 + 引用版本快照），与本仓既有的出生快照模式同构。但**未知项 1 未解**：在一条不依赖模型措辞的判据出现之前，本层的验收写不成「命令 + 期望输出」，因此不满足「可以做」的门槛。用户已明确此条留到设计阶段解决。
