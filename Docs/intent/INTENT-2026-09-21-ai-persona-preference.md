## Problem（问题与背景）

- 诉求：知芽目前只有一种固定的导师口吻。用户希望按学习处境切换风格，例如打基础时要「手把手」、冲刺时要「严格导师」、状态差时要「学习修复师」。
- 不做会怎样（**用户自述，2026-09-21**）：
  1. 回答显得**太水、学不到东西**——风格与当下处境不匹配时，用户拿不到需要的严格度与深度。
  2. 被迫**每次在提问里手动写风格要求**。这是当前的凑合方案，代价是重复劳动、容易忘、措辞不精确。
  3. 手写进提问的风格要求**会留在对话历史里**：回头看这条分支时，主线笔记里夹着一堆「你扮演严格导师」这类指令。内置人设是主题级设置，不进对话内容，因此不会污染主线。
- 现状（已核实）：用户可调的表达维度只有**模型**与**思考模式开关**两项，二者都不改变导师口吻与教学风格。
- 分期说明：本文件只承载**内置人设**。用户自建人设（用户输入提示词文本）是独立需求，见 `Docs/intent/INTENT-2026-09-21-user-authored-persona.md`。

### 已核实：内置人设与现有冻结边界完全兼容，不需要边界修订

关键依据是**思考模式开关**这个已经在生产代码里跑着的同构先例：

| # | 权威位置 | 内容 | 对本需求的意义 |
| :--- | :--- | :--- | :--- |
| 1 | `android/data/src/main/java/com/treelearn/data/db/TreeLearnSchema.java` 第 117、119、333 行 | `AnswerRevisions.THINKING_ENABLED` 是 `INTEGER NOT NULL CHECK (…)` 的真实列，注释写明「a revision stores the model and thinking mode that produced it」 | 证明「不影响提示词版本的行为维度 + 回答记录上的枚举列」已在生产运行；人设列同构 |
| 2 | `Docs/05-technical-design/知芽（TreeLearn）DeepSeek自适应学习导师提示词设计_V1.0.md` §8.1 与第 231 行 | 「思考开关只控制静态附加段，**不改变基础版本内容**，不接受用户插值」 | 内置人设的正确形态同为**静态、版本持有、追加**，不是改写基座正文 |

原先担心的五处冻结条目，**逐条比对后全部不成立**：

| V3.1 BASE-26 | 不得在提示词中插入**用户正文** | 内置人设不插入任何用户文本 |
| V3.1 BASE-26 | 不得借上下文文字改变 system 角色 | 人设不是上下文文字，是应用持有并显式声明的维度 |

| 建表规则第 44、45 行 | 没有任何列可以存放 system 提示词**正文** | 人设列存的是枚举身份，不是正文 |

结论：内置人设层**不需要任何边界修订**。本次唯一的边界动作是新增最高规则（见 Constraints）。

## Users and scenarios（用户与场景）

- 谁：单人自用，只有用户本人（既有非目标已冻结：无账号、无同步、无共享）。
- 典型处境与对应档位：
  - 进入陌生领域、完全没有基础 → **手把手**
  - 有基础、想被逼着思考 → **严格导师**
  - 想轻松探索、允许跑题 → **学霸搭子**
  - 学累了、只想有人陪 → **深夜陪读**
  - 想要一点压力和梗 → **毒舌损友**
  - 卡壳、挫败、自我怀疑 → **学习修复师**
  - 没有特别偏好 → **默认**
- 作用域（用户已确认）：**跟着主题走**。每棵树各自记住自己的选择。

## Expected outcome（预期结果）

- 用户能在主题内选定一种回答风格，之后新生成的回答在可观察行为上符合该风格；旧回答不被改写。
- 用户不再需要在提问里手写风格要求，主线笔记不会夹着这类指令。
- 主回答既有的导师基线（诚实、纠错、不编造）在任何一档下都不被削弱。

## Core flow（核心流程）

- 核心流程（含中断、撤销、重试）：
  1. 用户在主题内打开人设选择（与模型、思考模式同排）。
  2. 选择立即写入该主题，只影响之后新生成的回答。
  3. 下次进入同一主题，选择保持。
  4. 新建主题时的默认档：**「默认」**（2026-09-21 用户确认）。
- 输入/输出：输入是从固定 7 档中选一个；输出是主题级人设选择，以及每条回答记录上的人设身份。
- 状态与异常：沿用既有口径——切换只影响之后新生成的回答，不改写已有回答、来源版本或创建快照。
- 介绍页（2026-09-21 用户确认）：需要一个**人设介绍页**。
  - 职责边界：介绍页**不承担人设的选择**，选择只在主题内进行；介绍页负责各档的介绍与示例（示例为静态文案，不现场生成），并作为将来「人设增删改查」的承载位置。
  - 入口有两处，都要有：① 主题内「选择人设」弹窗里的一个按钮，进入介绍页；② 设置里的一个独立入口，直接进入介绍页（与主题入口各自独立，不互为跳转）。
  - 本期范围：只做介绍与示例；自建人设的增删改查属后续需求，本期只预留位置，不实现。

## Constraints and non-goals（约束与非目标）

- 约束：
  - 人设只能作用于**讲解方式、深度、节奏、措辞、是否主动反问、是否主动延伸**；不得触及事实准确性、纠错义务与不得编造。
  - 人设是**主题级**设置；不影响标题、分支摘要、推荐问题等派生输出，仅影响 AI 回答风格。
  - 人设身份必须是**可版本化的稳定枚举**，并随不可变回答记录落库，保证旧回答可复现。
  - system 消息恰好一条且位于请求第一位；当前输入位于最后一条。
  - 日志、测试报告与遥测不得记录提示词正文，只可记录用途与版本号。
  - Java-only；`:core` 不碰 Android UI、网络、数据库实现。
  - 单人开发：验收必须能机械验证。
- 本次需要新增的最高规则（**用户已确认口径**）：**「这个需求是否让用户学得下去、学得会」**。
  - 产品侧正文写一处；工程侧在 `AGENTS.md` 形成需求准入闸门。
  - 闸门里**只指向**产品正文，不复制内容——避免「一条规则两个正文」漂移（本仓失败案例库第一条例即为此坑）。
  - 措辞限定为「学得下去、学得会」而非「学习效率」：情绪价值档改善的是坚持率与体验，只写「效率」会把本次需求自己挡在门外。
- 权衡偏好：已确定优先**可复现与基线不被削弱**，人设自由度让位于此。
- 非目标（non-goals）：
  - 本期不做用户自建人设（见另一份文件）。
  - 本期不做「用户可编辑提示词正文」。
  - 不新增服务端、账号、同步；不引入非 DeepSeek 供应商。
  - 不改写既有 `LEARNING_ANSWER` 基线正文。
  - 不允许任何人设解除最高规则。

## Open questions（开放问题）

- 已确认事实：
  - 内置人设与冻结边界完全兼容，不需要边界修订（逐条比对见上表）。
  - 清单 7 档；行为定义落在 6 根轴：起点假设、信息密度、会不会反问你、会不会催你继续、表达情绪、会不会主动延伸。
  - 作用域跟着主题走；不影响派生输出；开关形态抄思考模式。
  - 需要人设介绍页，示例为静态文案。
  - 最高规则口径：「这个需求是否让用户学得下去、学得会」。

- 未知项（**不阻塞拆分**，可在设计阶段定）：

- 2026-09-21 用户拍板后消解的原未知项：介绍页入口位置（两处入口，见 Core flow）、新建主题的默认档（「默认」）。

## Convergence verdict（收敛判定）

### 有价值吗

结论：是
证据：用户给出三条可观察后果（回答太水学不到东西；被迫每次手写风格要求；手写要求污染主线笔记）。现状可调维度只有模型与思考模式两个旋钮，二者都不改变风格。证据等级：用户本人自述，尚无频次与量化数据。

### 值得做吗

结论：是
证据：不需要任何边界修订（逐条比对见上表），照抄已在生产运行的思考模式形态即可；受影响的任务均未开工（`T-2026-09-20-home-settings-ui-012` 与 `T-2026-09-20-chat-reasoning-answer-actions-013` 状态均为 `ready`）；与在开发的主链路无抢占。机会成本未量化，但内置层改动量小。

### 可以做吗

结论：是，**仅限内置人设层**
证据：架构接得住且有生产先例（证据 1、2）；无外部依赖；可切成多条垂直切片（见 Next step），每条都不动核心数据结构；验收沿用本仓既有的行为样例表模式，并有可机械验证的部分（人设枚举、主题列、回答记录上的人设身份、system 消息顺序）。**用户自建人设层不在这条结论内**，另见 `Docs/intent/INTENT-2026-09-21-user-authored-persona.md`。
