## Problem（问题与背景）

- 问题/背景：
  - **观察到的现象**：现有 Android 工程的表现层停留在 v1「生长绿」设计系统；用户已在 Figma 里做出精修稿（暖白纸感底 + 深绿墨色 + 衬线品牌字 + 线性图标 + 克制的描边与阴影），两者观感差距明显。新稿还改动了信息架构：引入底部标签栏，并把主题列表与归档内容从首页搬进独立的「学习库」屏。
  - **推测的原因**：v1 设计系统在 T-2026-09-20 的静态 UI 校验（`artifacts/evidence/T-013-static-ui-checks.txt`）前后定型；之后的功能切片（搜索、引用入请求、派生推荐、子分支弹层、阅读位置等）都沿用旧 token，没有再迭代过表现层。
  - 两侧是**同一产品**：新稿内嵌的 PRD 与工程内 `Docs/03-prd-draft/V3.1-知芽（TreeLearn）产品需求文档（PRD）.md` 的 md5 完全一致，所以新稿是「对着同一份规格画出来的精修版」，不是另一套产品。
- 用户/场景：
  - 唯一用户是产品经理本人，同时是唯一决策人与唯一复核者。
  - 场景：在 Android 手机上学习陌生领域；发起学习、在分支之间导航、用画布看整棵树、检索已学内容、整理不再需要的探索路径。

## Users and scenarios（用户与场景）

- 谁：产品经理本人（单人开发，没有第二类用户，也没有协作方）。
- 什么情况下：
  1. 通勤或碎片时间在手机上发起一个新主题；
  2. 阅读 AI 回答时对某一段产生疑问，分叉成独立分支继续深挖；
  3. 回头看整棵树都长出了哪些方向（画布或分支导航）；
  4. 想找回几天前学过的某个结论，但只记得关键词；
  5. 某条探索路径已经走完，想把它从日常视线里收起来。
- 本期是否只有自己用：是。因此不需要多用户、权限、同步、协作类设计。

## Expected outcome（预期结果）

做完之后，以下可观察的变化应当成立：

1. 打开 App 看到新稿的配色、圆角、字号与品牌字（暖白纸感底、深绿墨、衬线品牌题字），且正文与次要文字的对比度全部达标。
2. 底部出现三个标签：主页 / 学习库 / 设置。主题列表与归档内容集中在学习库。
3. 首页只剩四块：品牌区、输入区、继续学习、发现话题。
4. **功能一项不少**（这是本轮的红线）：
   - 归档仍可执行，入口在分支导航屏的分支操作里；
   - 检索仍覆盖 PRD 规定的全部字段，入口是学习库顶部的一个搜索框，结果在学习库列表区呈现并带祖先路径与归档状态；
   - 删除仍是整棵子树，仍需二次确认且不可恢复。

## Core flow（核心流程）

- 核心流程（含中断、撤销、重试）：
  - **主路径 A（学习）**：启动 → 主页输入根问题 → 对话页 → 追问或从某段分叉 → 用画布或分支导航查看结构 → 回学习库回查。
  - **主路径 B（整理）**：进入分支导航屏 → 对某个非根分支执行归档 → 该分支与其整棵子树从日常导航与默认画布隐藏 → 在学习库「已完成」区可整体恢复，或经二次确认永久删除。
  - **主路径 C（查找）**：在学习库顶部的搜索框输入关键词 → 结果区展示命中项（含祖先路径与归档状态）→ 点进入对应分支或定位到锚定原文。
  - **中断**：生成中断保留已产出的部分内容，可原位重试，不重复创建消息或分支（沿用现状）。
  - **撤销**：归档可整体恢复，且恢复时不把任何后代重接到别的父节点（沿用现状）。
  - **重试**：失败回答原位重试；迟到的生成响应被丢弃而不是渲染（沿用现状）。
- 输入/输出：
  - 输入：根问题、追问文本、搜索关键词、归档/恢复/删除指令、模型档位与思考开关。
  - 输出：树形结构（主题 → 分支 → 消息/回答版本）、AI 回答、检索结果列表、学习库的主题与归档列表。
- 状态与异常：
  - 无可用 Key 时不创建主题，只在首页给提示（沿用现状）。
  - 搜索失败时保留草稿并显示错误态；搜索中显示进行态；无结果与「尚未搜索」是两个不同状态。
  - 删除是不可恢复操作，必须经二次确认，且确认前先取消在飞的生成。

## Constraints and non-goals（约束与非目标）

- 约束：
  1. **红线：这次只是交互与表现的调整，不能影响功能的规格。** 允许变化的是入口位置、导航结构、视觉 token、组件形态；不允许变化的是功能的有无与语义。
  2. 零 AndroidX、Java-only、不新增第三方依赖（`android/scripts/no-kotlin-check.ps1` 会把关）。
  3. 设计 token 三处同步：原型 `:root` → `tokens.json` → `colors.xml`，之后跑 `check_design_tokens.py`。
  4. 单任务生产代码行目标不超过 200，超过 500 为失败（口径：非空非注释行，用户 2026-09-21 裁定）。
  5. 本轮不打包字体：正文用系统 `sans-serif`，品牌字先用 `serif` 族回退。
- 权衡偏好：
  - 宁可分批交付可独立验证的切片，也不做一次性大改。
  - 宁可保留功能的最朴素入口，也不砍能力换观感。
  - 出现设计稿与生产代码冲突时，按「生产代码是事实、设计稿是意图」记录偏差并单独路由。
- 非目标（non-goals）：
  1. 不新增任何功能，不调整任何已有功能的语义。
  2. 不做暗色模式。
  3. 不迁移原型的内存数据模型与演示假数据（`src/data.ts` 的 DEMO 内容）。
  4. 不改动已验收的纯 Java 树布局算法；画布只做装饰性叠加。
  5. 不把新稿的 SVG 布局常量搬到工程。
  6. 不把独立搜索屏直接删掉而不承接它的检索能力。

## Open questions（开放问题）

- 已确认事实：
  - 新稿内嵌 PRD 与工程内 V3.1 PRD md5 相同（`a4d8fe8c42f5192ce442d6c2342eb26c`）。
  - 工程配色 100% 走 `tl_*` token，间距/圆角/字号 100% 走 `res/values/dimens.xml`。
  - 工程 `res/drawable/` 无任何 UI 图标；无 `res/font/` 目录。
  - `SearchDao` 是七臂 `UNION ALL`，逐字段检索标题、问题、锚定原文、回答、思考、失败尝试的半成品内容。
  - 新稿的库内过滤框只比较主题根标题/摘要与已归档分支的标题/摘要，日常非根分支搜不到。
- 假设：
  - 新稿的「简约高级」观感主要来自配色、字形、图标与克制的描边，而不是底部标签栏本身。
  - 底部标签栏是设计稿不可退让的部分，决定了首页的瘦身形态。
- 未知项：
  - Vector Drawable 这类 XML 资源是否计入生产代码行预算——需按 `.codex/scripts/dev/count_production_lines.py` 的实际口径确认，不凭猜。

## Convergence verdict（收敛判定）

### 有价值吗

结论：是
证据：用户已独立完成 Figma 精修稿，说明观感差距是其真实痛点；且新稿的配色在对比度上整体优于现稿（除 `ink3` 与 `amber` 两个 token 需修正，实测见方案文档与对比度审计脚本）。

### 值得做吗

结论：是
证据：两侧是同一产品，迁移性质是「换底 + 改壳 + 补件」而不是重写。第一层只需改四个文件（原型 `:root`、`tokens.json`、`colors.xml`、`dimens.xml`）就能让整个 App 迭代到新设计，投入产出比极高。

### 可以做吗

结论：是
证据：颜色已 100% token 化、度量已 100% 走 `dimens.xml`，改色有守门脚本兜底；新 IA 所需的学习库屏是新增，不必重写现有屏；`MainActivity` 的单 Activity 换屏机制已支持注册新屏。
