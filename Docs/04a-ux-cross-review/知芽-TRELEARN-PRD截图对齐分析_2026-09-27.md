## 0. 结论先行

1. **上一轮的 5 维结论不必推翻**；但 **6 条问题需要改写或降级**——它们大多不是「实现做错了」，而是**PRD 自己有缺口（未定义），实现只是如实暴露了缺口**。
2. **截图 4（学习树页）重新判定**：不是「缺 loading / 坏页」，而是**「单主题、单主干、单叶的新树在画布上被缩到几乎不可见」**——底部那行极小字 + 绿色叶芽 + 灰色横条，正是 PRD 要求的 `根节点嫩芽标记` + `叶子` + `底部土地暗部/主干`，说明**画布渲染了、只是没有最小可识别形态**。归属：**PRD 未定义（§6.2.7 缺「最小树/最小缩放/标题牌字号下限」边界规则）为主，实现层可优化为辅**。
3. **「你好」被当成学习记录**：PRD §6.2.1 的首次创建原子性**只校验 Key 可用性，没有任何输入质量约束**——所以「你好」成为主题**符合 PRD**，这是**需求缺口（PRD 未定义输入下限）**，不是 UI bug。
4. **用户自己发现的两处文档冲突，判定成立**：① §6.2.18-2「设置页不提供模型配置项」与 V3.3 FR-3「模型设置页三分工」**直接冲突**；② 设置页 Key 双入口**部分成立**——SPEC providers 其实**有意**保留 Key 卡作「默认提供商 Key 快捷入口」，所以不算结构性重复，但**「DEEPSEEK API KEY」把默认提供商写死**，与 V3.3 多 Provider 冲突（文案级冲突）。
5. 本轮的**高价值动作 = 补 4 条 PRD 边界规则 + 仲裁 1 处文档冲突 + 修正 3 处文案/符号**，全部是低代价、可机械验收的。改动代价普遍为**低–中**，唯一「中」是画布最小树形态与首页热力条（涉及渲染与测试）。

## 3. 优化方案（按 PRD 条款组织）

> 数值只写 token 名（`fs-*` / `s1..s8` / `r-*` / `sh-*` / `lh-read` / 颜色名）；验收尽量写成可机械验证的断言。

### 批次一 · 止血（对应 §6.2.7、§6.2.13、§6.2.16-1；代价：中）

**M1｜补 §6.2.7 画布边界规则并落地渲染**（对应改写后的 P0-1）
- **改什么**：给 §6.2.7 增加「最小树形态与最小缩放」子条（草案见 §5-N1）。
- **改成什么样**：单主题/单主干时，画布进入默认缩放后，必须保证**主干 + 叶 + 嫩芽标记**在屏幕上达到最小可识别尺寸；「适应屏幕」对单节点树设**缩放上限**（不得把可见树缩到低于最小尺寸）；叶子标题牌字号取 `fs-cap`，缩放不得使其低于该档。
- **验收（机械可验）**：新增画布断言测试——(a) 单主题 1 轮时，主干渲染高度 ≥ 阈值、叶可见；(b) 点击「适应屏幕」后缩放比 ≤ 约定上限；(c) 标题牌 measuredTextSize == `fs-cap` 对应值。

## 4. 需要用户拍板的事项（建议 + 理由 + 代价）

> 按本项目沟通契约，每项三段式。

1. **画布「最小树形态」是补 PRD 规则还是只当实现 bug？**
   - **建议**：补 PRD 规则（§6.2.7 增子条），再按规则渲染。
   - **理由**：截图4 的元素（叶芽/主干/土地/标题牌）都符合 PRD，说明渲染逻辑没错，缺的是**没有约束下限**；只修实现会反复回归。
   - **代价**：补文档低；落地渲染与测试中。

2. **根问题是否加输入质量下限（「你好」问题）？**
   - **建议**：**不加硬约束**（不禁止），但在 PRD 显式写明「首版不设根问题最小长度/内容过滤」，把「你好成为主题」定性为**用户自身可控行为**而非缺陷；如需，仅加「空白/纯空格」拦截。
   - **理由**：这是个人自用 App，等于用户本人输入；硬做 NLP 过滤会引入误伤与额外依赖，收益低。
   - **代价**：低（一条声明）；若做过滤则中。

3. **命名统一方案是否采纳「学习库/画布/分支导航/设置/统计」？**

   - **理由**：四个「学习X」近义并存会让用户（和未来的你）无法建立稳定心智模型。
   - **代价**：低（改字符串资源 + 更新受影响测试断言）。

   - **代价**：低。
