## 0. 结论先行

1. **功能侧不需要做任何取舍**。截图里出现的每一个按钮，当前原型都有同款且位置一致；原型多出的按钮只在特定数据下出现。所谓「融合」实际是**只调视觉、不动交互**。
2. **视觉侧最终只有 3 处需要改**：正文字体、用户气泡底色、用户气泡圆角。（初稿曾列 4 处，第 4 处「AI 标识行下方间距」经 DOM 实测判定为**假差异**，见 §3 差异 4。）其余 **28 项实测已 1:1**，无需改。
3. 其中**字体是唯一有全局影响的改动**，而且它的方向与生产实现一致：Android 侧 `themes.xml` 现在就是 `sans-serif`，原型的楷体反而是与真机不符的那一方。
4. 唯一需要你放宽既有约定的地方是**用户气泡底色**：新增这个色值会让 Android `colors.xml` 的资源数从 15 变 16，而 `tokens.json` 里写着「本轮不改动它的 15 个资源名与数量」。

## 1. 范围与非目标

**范围**：对话页（`ChatScreen`）的样式对齐 —— 消息流、AI 回答区、回答动作行、推荐问题区、AppBar、页面底色。

**非目标（本次不做）**：

- 截图底部被裁切，**输入栏（composer）全貌不可见**，因此输入栏保持现状，不参与本次比对。
- 截图未覆盖：思维链折叠区、失败条、归档提示、来源条、引用卡、未读提示、子分支弹窗。这些一并在本次保持现状。
- 不改交互语义、消息顺序、分支模型、阅读位置锚点。
- 不改 Android 生产代码（`item_chat_message.xml` / `screen_chat_body.xml`）。Android 落地是 074–076 的范围，本次只对齐 HTML 原型。

## 2. 实测方法

截图为 2x 截图（物理 824×1367 → 逻辑 412×684dp），**逻辑值 = 物理值 / 2**。用纯 Python 解码 PNG 后逐行扫描，按元素类型做颜色聚类与边界测量。所有数字来自证据文件的对应小节，可重跑复核：

```bash
# 2026-10-15 起仪器已入库并可按屏名重跑（当年这条命令跑的是 artifacts/tmp/ 下的同名脚本）。
# 重跑请写到新文件名：本节下面引用的 ux-chat-1to1-measure-2026-09-27.txt 是当年的实测记录，
# 覆盖它就等于改写当年的结论。
python -X utf8 .trae/scripts/dev/parity/measure_screen.py --screen chat \
    > artifacts/evidence/ux-chat-1to1-measure-2026-10-15.txt
```

判断色值是否"被改过"的**对照基线**：同一张图里的正文墨色与图标灰。

| 元素 | 截图实测 | 原型 token | Δ(ΔR,ΔG,ΔB) |
|---|---|---|---|
| 正文文字 | `#19231D` | `ink` `#16241C` | (3, −1, 1) |
| 回答动作行图标 | `#656F68` | `ink3` `#627067` | (3, −1, 1) |
| 推荐项内分叉图标 | `#656F68` | `ink3` `#627067` | (3, −1, 1) |
| ✦ 星形图标 / 「知芽」 | `#223F29` | `green-deep` `#164027` | (12, −1, 2) |
| **用户气泡底** | **`#3F6C49`** | **`green` `#2B6E45`** | **(20, −2, 4)** |

前 4 项的偏差都在抗锯齿范围内（≤3），小字 11px 的 `green-deep` 偏差 12 也可由细笔画抗锯齿解释。**只有用户气泡偏了 20，且它是 27716 个像素完全同色的大面积纯色区——抗锯齿解释不了。** 所以这不是"整张图偏色"，而是**只有气泡绿被改过**。这条基线是下面所有判定的前提。

## 3. 差异清单（初稿列 4 处；实测判定 **3 处需改、1 处为假差异**）

### 差异 1 · 对话页正文字体：楷体 → 无衬线黑体（影响最大）

| | 事实 |
|---|---|
| 截图 | 无衬线黑体。放大 6 倍看「收到，我们开始系统学习」：横竖等宽、方头方尾、无笔锋；拉丁 `Transformer` 为无衬线等线体 |
| 原型（改动前） | `.screen{font-family:var(--kai)}`（第 114 行）= 霞鹜文楷，对话页全部文字继承楷体 |
| 生产 | `android/app/src/main/res/values/themes.xml:11` → `<item name="android:fontFamily">sans-serif</item>` |

**建议改法**：把 `.screen` 的 `font-family` 从 `var(--kai)` 改为 `var(--sans)`。

**理由**：截图用黑体，真机也是黑体，只有原型在用楷体——改完原型才第一次"拍得出真机的样子"。这是消除设计稿与生产偏差，不是引入新风格。

**代价**：`.screen` 是共享容器，对话页之外的正文（首页 hero 副标题、话题卡摘要、分支导航、画布标签、搜索/归档/设置页）一起变黑体。品牌衬线不受影响——`.home-hero .hh-name`、`.hh-title` 显式用 `var(--serif)`，品牌识别保留。

**另需注意**：`--kai` 改完后只剩 `.home-hero .hh-sub` 一处还在引用。若这处也改掉，`--kai` 与字体 CDN 链接（霞鹜文楷两条 `link`）即可退役——这会在下方拍板项 A′ 里一并决定。

> **执行状态（2026-09-27）**：✅ **已执行**。原型第 114 行 `.screen` 的 `font-family` 由 `var(--kai)` 改为 `var(--sans)`（带行内注释记录原因）。按 A′ 建议**本轮保留 `--kai`**，因此两条霞鹜文楷 CDN `link` **不可移除**；`--kai` 的注释已更新为「现存唯一引用是 `.home-hero .hh-sub`」。
>
> **改动仅此一处，未增删 token** —— token 数 44、资源数 16 均不变。
>
> **四项独立判据（防"CSS 写了但实际没生效/静默回退"）**：
> ① 声明值回读 `"Noto Sans SC", -apple-system, sans-serif`；
> ② `document.fonts` 注册面 = `Noto Sans SC` **400 / 500 / 700** 三档（字体真实存在，不是回退到系统 sans）；
> ③ `CSS.getPlatformFontsForNode` 读出**实际参与栅格化**的字体为自定义 webfont（`custom: true`）；
> ④ 同字符串、同盒子、同换行的**墨量 A/B**：气泡内白字像素 **13794 → 15355（+11.3%）**，方向符合楷体（笔画细、粗细有变化）→ 黑体（方头等线、笔画更粗）。
>
> ③ 有一个读数陷阱已写进 §10.5：该接口返回的是**字体文件内部名** `Noto Sans SC Thin`（变量字体的默认实例名），**不等于渲染字重**——字重必须看 ② 的注册面，不能看到 "Thin" 就以为渲染成了细体。

### 差异 2 · 用户气泡底色 `#2B6E45` → `#3F6C49`

| | 事实 |
|---|---|
| 截图 | `#3F6C49`（27716 像素同色，见 §2 基线表） |
| 原型 | `.msg-user{background:var(--green)}` = `#2B6E45` |
| 对比度 | `#3F6C49` 上白字实测 6.07:1（现状 6.14:1），**AA 无风险** |

**建议改法**：**新增一个专用 token 给用户气泡**，不动主色 `--green`。建议命名 `green-bubble`，值 `#3F6C49`。

**理由**：`--green` 是「生长绿」动作色，服务于发送键、主按钮、锚点下划线、生成中圆点、叶芽标记等**小面积、需要"跳"出来**的元素。气泡是**大面积底色**，设计上本就可以用一档更柔和的绿来降低压迫感——截图正是这么做的。把两者分开，才能既对齐截图、又不让按钮一起变灰。

**代价**：新增 1 个不透明 hex token，守门脚本（`.trae/scripts/dev/check_design_tokens.py` 第 145 行按不透明 hex 自动映射）会要求 `colors.xml` 同步新增 1 个资源 → **15 → 16 个**。这与 `tokens.json` 中 `green-soft` 条目写明的「本轮不允许改动它的 15 个资源名与数量」冲突，**需要你明确放宽该约定**。

**备选（若不接受放宽约定）**：把 `--green` 的值直接改成 `#3F6C49`。这样资源数量不变（只改 `tl_green` 的值），守门照样绿；代价是所有绿色元素一起变浅——但这些元素截图里看不到，改完后**无法验证它们变浅是否还合适**。

> **执行状态（2026-09-27）**：✅ 已按建议执行——采用**新增 token** 方案（未走备选），`--green` 保持 `#2B6E45` 不动。三处同值，资源数 15 → 16，守门 `EXITCODE=0`。

### 差异 3 · 用户气泡圆角：左下角 4px 尖角 → 四角统一

| | 事实 |
|---|---|
| 截图 | 四角**完全对称**。inset 序列 top 侧 `23,13,8,5,3,1,0` 与 bottom 侧 `23,13,8,5,3,1,0` **逐值相同**；**前向拟合**半径 R = 26.5 物理 = **13.2 逻辑 px** |
| 原型 | `.msg-user{border-radius:var(--r-md) var(--r-md) var(--s1) var(--r-md)}` → 14/14/**4**/14，左下角是尖角 |

**建议改法**：`border-radius: var(--r-md)`，四角统一 14px。

**理由**：截图没有"尾巴"这个语汇。实测 13.2 与 `--r-md` 的 14 只差 0.8，落在抗锯齿带内，用既有档位即可，不新增圆角档。

**代价**：无。这是纯 CSS 一行。

> **量测方法更正**：本节初稿写的是「inset 归零于 top+23 物理 ⇒ ≈12 逻辑 px」。该反解方法对 ±2 的抗锯齿误差极敏感（同一组数据反解会在 8~24 物理间乱跳），已改为**前向拟合**：对候选 R 预测整条 `inset(dy)` 曲线取残差平方和最小者 → 13.2 逻辑 px。同一支拟合脚本量原型渲染图得到**同为 13.2**（见 §10），是本次闭环最干净的一条。
>
> **执行状态（2026-09-27）**：✅ 已执行 `.msg-user{border-radius:var(--r-md)}`。"左下角 4px 尖角"这个语汇已从原型移除。

### 差异 4 · AI 标识行与正文间距 —— **回滚：本条差异不存在**

| | 事实 |
|---|---|
| 截图 | 「✦ 知芽」标签中心 y=196 → 正文首行中心 y=236.5，**中心距 40.5 逻辑 px** |
| 原型（初稿估） | 按「tag 行盒高 20」估算 ⇒ 中心距 **33** |
| 原型（DOM 实测） | `.ai-tag` 行盒高 **28**（它继承了 `.msg-ai` 的 `line-height:28px`，不是被 11px 字号撑成 20），`margin-bottom:12`，正文行高 28 ⇒ 中心距 = 28/2 + 12 + 28/2 = **40** |

**结论**：原型现值 **40** 与截图 40.5 只差 0.5 —— **本条是初稿估错 tag 行盒高（20 vs 实则 28）算出来的假差异**，不需要改。上表「原型现值 33」应按此更正为 40。

> **试改后回滚**：曾按原建议加 `min-height:20px` + `margin-bottom:--s4`，会把中心距推到 44（离截图比现状更远），故撤回，恢复 `margin-bottom:var(--s3)` 且不加 `min-height`（后者对行盒已 28 的元素本就是空声明，当前 DOM 计算值 `min-height:0px`）。
>
> **连带更正**：本文档初稿「4 处需要改」应更正为 **3 处**（字体、气泡底色、气泡圆角）。

| 圆角用反解对噪声过敏 | 同一组 inset 数据反解出 8~24 物理 px 乱跳 | 改**前向拟合**（预测整条 `inset(dy)` 曲线取最小残差）——截图与渲染两侧都得 **13.2** |
| 胶囊底色精确匹配 | 截图 `#EBE9E5` vs 渲染 `#ECEAE4` 差 1 ⇒ 渲染图上胶囊数被判为 **0** | 容差 ±2，并**显式排除纸感格线色**避免串味 |
| 脚本只认一种 AppBar 制式 | 渲染图（AndroidFrame 32px 状态栏）令 §2 抛异常，整份证据输出中断 | §2 及各节改为「检不到就跳过并写明原因」，不再中断整份证据 |
| 截图与证据可能不同源 | `captureBeyondViewport` 用错会输出一整片纯色，看起来"截到了" | 测量脚本加**废图自检**（四角取样同色即报「疑为无效截图」）＋ 左缘深色带自动量宽并声明校正量 |
| 字体面回读恒为空且**不报错** | `Array.prototype.forEach.call(document.fonts, …)` 迭代 **0 次**，输出空数组，看起来像"一个字体都没注册" | `FontFaceSet` 是 Set 语义（只有 `size`、没有 `length`）→ 改 `Array.from(document.fonts)` |
| `getPlatformFontsForNode` 的族名被误读成字重 | 回读 `Noto Sans SC Thin`，容易被读成"渲染成了细体" | 该接口返回的是**字体文件内部名**（变量字体的默认实例名），**不是**渲染字重；字重必须看 `document.fonts` 的注册面（实测 400/500/700），并用墨量 A/B 交叉验证 |
