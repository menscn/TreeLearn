## 0. 一句话结论

这不是「换一套皮肤」，而是**同一产品的精修版**：新稿的配色/度量/组件细节整体比现工程更稳，可以直接吸收；但它同时**改了信息架构**（引入底部标签栏 + 独立「学习库」屏），并且**丢掉了 4 项已被 PRD 冻结的 P0 能力**。所以迁移必须分三层做，且第一层之前要先修掉新稿自身的两处对比度回退。

### 红线（用户 2026-09-22 明确）

> **「这次只是交互的调整，不能影响功能的规格！」**

这条约束**优先于**本方案的所有其他建议，是本轮迁移的判定基准：

- **允许变化**：交互路径与表现层——入口位置、导航结构、视觉 token、组件形态。
- **不允许变化**：功能的有无与语义——归档/删除的整树语义、四字段全局检索、祖先路径与归档状态的展示。
- **推论**：§2 C 类那 4 项新稿缺陷（归档入口丢失、删除不删子树、缺祖先路径、搜索降级），**一律按 PRD 保留原功能**，只把它们的入口与视觉迁到新 IA 上，不为迁就设计稿而削减任何一项。

## 2. 差异分类

### A 类 · 可直接吸收（配色与度量）

新稿的 16 个语义色 + 间距 + 圆角 + 字号全套可以吸收，且**整体优于现工程**。实测 WCAG 对比度（对比对象：旧 = `#F7F6F0` 底，新 = `#F4F1EB` 底；判定阈值取正文 4.5:1）：

| token 用途 | 旧值 | 旧对比度 | 新值 | 新对比度 | 结论 |
| :--- | :--- | ---: | :--- | ---: | :--- |
| `ink` 正文/主标题 | `#1E2B23` | 13.61 | `#16241C` | 14.29 | 新更好 |
| `ink2` 次要文字 | `#5A6B60` | 5.23 | `#435449` | 7.16 | 新更好 |
| `ink3` 弱化/标注 | `#636F66` | 4.85 | `#75867B` | **3.42** | ⚠️ **新稿回退，不达标** |
| `green` 主色（作文字用） | `#2E7D4F` | 4.66 | `#2B6E45` | 5.45 | 新更好 |
| `blue` 未读点 | `#2F6BFF` | **4.16** | `#2563EB` | 4.58 | 新修好了旧稿的缺陷 |
| `amber` 警示 | `#B7791F` | **3.36** | `#B45309` | **4.45** | 新旧都不达标，新已接近 |
| `red` 危险 | `#C0392B` | 5.02 | `#C0392B` | 4.82 | 一致，达标 |
| 白字 on 主色按钮 | — | 5.05 | — | 6.14 | 新更好 |
| `ink3` on 卡片面 | — | 5.26 | — | **3.72** | ⚠️ 同上，不达标 |

**必须修的 2 处（否则等于把一个已验证达标的工程改坏）**：

1. `ink3`：`#75867B` → 建议 **`#627067`**（保留原色相只压暗一档，实测 on bg 4.62 / on surface 5.03，均达标，且层次接近旧稿的 4.85/5.26）。
   最小改动方案是 `#637269`（4.50 / 4.90）——正好压在阈值上**没有余量**，不建议采用。
2. `amber`：`#B45309` → 建议 **`#B05108`**（实测 on bg 4.63 达标）。最小改动方案是 `#B25209`（4.54）。
   注意旧稿 `#B7791F` 本来就是 3.36 不达标，这次是**顺手补上一次历史欠账**。
   补充一处细节：`amber` 在新稿的卡片面（surface `#FCFBF8`）上是 4.85 达标的，只有落在底色 `#F4F1EB` 上时才 4.45——受影响的只有 `.fail-bar`（失败提示条，落在消息流底色上）。

> 上表与修正值均由一个可重跑的脚本产出，不是目测：
> `python ~/.workbuddy/skills/design-migration-audit/scripts/contrast_audit.py table --old-bg "#F7F6F0" --new-bg "#F4F1EB" --surface "#FFFFFF" --new-surface "#FCFBF8" ink:#1E2B23:#16241C ink2:#5A6B60:#435449 ink3:#636F66:#75867B green:#2E7D4F:#2B6E45 blue:#2F6BFF:#2563EB amber:#B7791F:#B45309 red:#C0392B:#C0392B`
> 脚本退出码非 0 表示存在"旧达标、新不达标"的回退项，可直接用在第 1 层的验收里。

> 这两处修正必须**先落回新稿的 `:root` 权威位置**，再同步 `tokens.json` 与 `colors.xml`，最后跑守门脚本——这是 `ux-design.md` 明文规定的固定顺序，跳过任一步守门会变红。

### B 类 · 需要你拍板的 IA 变更

新稿引入**底部标签栏**（主页 / 学习库 / 设置），并把「主题列表」与「归档内容」从首页搬进独立的**学习库**屏。这直接与已冻结的 PRD 规则冲突：

> PRD V3.1「首页信息架构统一」条目原文：
> 「首页为唯一入口页，包含固定的品牌头部；头部右侧依次提供搜索、已归档、设置三个入口」
> 验收口径：「首页含品牌头（搜索/归档/设置）+ 常驻根问题输入框 + 推荐区 + 历史主题列表；**无第二套首页**」

也就是说：**新稿的首页不再是唯一入口页，且出现了"第二套列表"**。这不是样式改动，是产品架构改动，必须走 PRD 增量，否则迁移完成后工程与已验收的 PRD 自相矛盾。

### C 类 · 迁移时必须补回（新稿自身的功能缺陷，不能照搬）

逐条核对新稿与 PRD 后，发现 5 处不能照搬：

1. **归档入口整个丢失**。在来源 `src/` 下全文检索「归档」，只命中 PRD 文本与 `data.ts` 里预置的 `archived: true` 演示数据；`src/screens/` 下**没有任何可触发归档的界面**。而学习库的「已完成」标签能恢复、能删除，却没有任何地方能把分支放进去。PRD 里 **F10「非根子树归档与永久删除」是 P0**（`V3.1` 第 506 行）。
   → 迁移时必须补回归档入口。建议落在**分支操作菜单**里（与现工程 `NavigationPresenter` 的归档动作对齐），因为归档的对象是「非根父分支及其整棵子树」。

2. **删除只删一个节点、不删子树**。新稿 `App.tsx` 的 `deleteBranch` 用 `const { [branchId]: _, ...rest } = d.branches` 只移除自身，父节点 `children` 里的 id 变成悬空引用。PRD 要求「经确认永久删除目标非根父分支及**全部后代**」。
   → 迁移时按 PRD 实现整树删除。

3. **「已完成」列表缺祖先路径与归档状态**。新稿只显示根主题名 + 锚点原文；PRD 要求「每条搜索结果显示祖先路径及归档状态，支持定位日常分支和已归档非根子树中的分支」（F08、F10）。
   → 迁移时补齐祖先路径展示。

4. **全局搜索被降级成本地过滤框，且独立搜索屏成了死代码**。新稿 `src/screens/SearchScreen.tsx`（91 行）存在，但 `src/App.tsx` 的 `Screen` 类型只有 `home | chat | nav | canvas | settings | archive`，**从未导入或路由到 SearchScreen**。搜索被替换成学习库里的一个输入框，只能筛「主题标题+摘要 / 归档分支标题+摘要」。
   而 PRD 要求全局检索**标题、问题、回答、锚定原文**四类字段并跨归档状态（F08/F09，均为 P0），现工程 `screen_search_body.xml`（132 行）+ `SearchPresenter`（162 行）已完整实现。
   → **这是本次迁移最大的功能倒退风险**：若照搬新稿，等于删掉一个 P0 能力。迁移时需为搜索重新安家（建议保留独立搜索屏，入口放在学习库头部 + 首页头部快捷位，而不是降级成过滤框）。

5. **新稿的数据模型是原型内存模型，不能作为迁移目标**。`src/data.ts` 用 `Record<string, Branch>` + `children: string[]` 在内存里拼树，交互全在 `useState` 里，无持久化、无生成流程（"生成中"是假动画）、无错误恢复。工程侧已有真实的 SQLite 父子关系、`NavigationStore`/`TreeCanvasStore`/`GenerationCoordinator`。
   → **迁移的东西是「视觉与交互规格」，不是数据层**。`DEMO` 里的注意力机制 / 冷链物流样例只是演示内容，不迁移。

### D 类 · 缺口（设计稿要求、现工程没有，属新增工作量）

| 缺口 | 现状 | 工作量性质 |
| :--- | :--- | :--- |
| **UI 图标资产** | 工程 `res/drawable/` 零 UI 图标，现界面上"图标"全是中文文字按钮（`android/README.md` 有记录） | 需新建约 **28 个 Vector Drawable**（24dp 网格 / 1.8 描边 / 靠 tint 上色）。**独立工作流，可单独切片** |
| **字体** | 工程零自定义字体。旧设计系统要求的楷体（霞鹜文楷）从未落地 | 见 §5 待拍板第 2 条。**建议正文用系统 `sans-serif` 零成本**（Android 中文设备的系统 sans 本就是 Noto Sans CJK 系），品牌字先用 `serif` 族回退，暂不打包 |
| **新组件** | 新稿有 10 个工程侧不存在的组件/模式 | 底部标签栏、分段控件、Toast、底部 sheet、开关、单选列表、状态徽章、虚线锚点文本、生成中动效、画布点阵网格 + 缩放工具栏。多数可用平台控件或自绘 View 实现，**但须逐个确认不违反零 AndroidX 约束** |
| **多尺寸适配** | 工程有 `layout-sw600dp/` 一套（画布为真双列结构） | 新增的底部标签栏、学习库屏都要补 sw600dp 版本 |

## 3. 迁移路线：三层推进

「有机迁移」的落法是把风险分层隔离，而不是一屏一屏地重写。理由：第一层零逻辑风险但能让全 App 立刻变新；第二层是唯一改产品语义的层；第三层是纯增量，可以慢慢来。

### 第 1 层 · 设计基座替换（不动任何交互逻辑）

| 项 | 内容 |
| :--- | :--- |
| 目标 | 全 App 换上新配色与度量，交互行为一字不改 |
| 可写路径 | `Docs/04-ux-design/知芽-TreeLearn-高保真原型-v1.html`（`:root`）、`Docs/04-ux-design/design-system/tokens.json`、`android/app/src/main/res/values/colors.xml`、`android/app/src/main/res/values/dimens.xml` |
| 前置 | **先落地 §2 A 类的 2 处对比度修正**（`ink3` → `#627067`，`amber` → `#B05108`） |
| 验证 | `python .codex/scripts/dev/check_design_tokens.py`（三方逐值比对）0 failure + `--selftest` 正反自检通过；`android/README.md` 的对比度条目同步更新 |
| 风险 | 低。唯一硬约束是「三处必须同步，顺序固定」 |

**这一层做完，整个 App 的观感就已经迭代到新稿了。**

### 第 2 层 · 外壳与信息架构对齐（唯一改产品语义的层）

| 项 | 内容 |
| :--- | :--- |
| 目标 | 底部标签栏 + 学习库屏 + 首页瘦身 |
| 前置 | **先写 PRD 增量条**（V3.2 或 V3.1 增量文档），明确「首页不再是唯一入口页」「主题列表迁至学习库」「搜索入口新位置」 |
| 可写路径 | `android/app/src/main/java/com/treelearn/app/MainActivity.java`（`swap()` 换屏 + 新屏注册）、新增 `screen/LibraryScreen.java` + `ui/LibraryPresenter.java` + 对应 ViewState、`screen/HomeScreen.java` 与 `res/layout/screen_home_body.xml` 瘦身、新增 `res/layout/screen_library*.xml` |
| 必须一并处理 | §2 C 类第 1/3/4 条（补归档入口、补祖先路径、给全局搜索重新安家） |
| 验证 | 对话页/导航页归档路径的仪器测试（现已有 `NavigationStoreInstrumentedTest`、`TreeCanvasStoreInstrumentedTest` 可作为模板）；搜索四字段检索能力不得退化 |
| 风险 | **高**。这是唯一会改变用户可见产品结构的一层，也是唯一必须改文档的层 |

### 第 3 层 · 组件与细节补齐（纯增量，可自由切片）

- 28 个 Vector Drawable 图标资产（新建独立目录 + 命名约定，先建一个再批量）
- 组件视觉：chip / 状态徽章 / 分段控件 / 开关 / Toast / 底部 sheet
- 画布点阵网格背景 + 缩放工具栏（现 `TreeCanvasView` 已自绘，属增强）
- 字体策略落地
- `layout-sw600dp/` 补齐新屏

## 4. 切片建议与流程风险

**最大流程性风险：单 task 500 行硬预算**（`.codex/skills/line-budget/line-budget.ps1`）。对照现状：

| 屏幕 | 现有体量 | 能否单 task 完成 |
| :--- | ---: | :--- |
| 首页 | `HomeScreen.java` 260 + `screen_home_body.xml` 273 = **533 行** | ❌ 已超预算 |
| 对话 | `ChatScreen.java` 640 + `item_chat_message.xml` 168 = **808 行** | ❌ 已超预算 |
| 学习库 | 全部新增 | ✅ 可控制在 400 行内（新屏从零写，按区块切） |

→ **任何一屏的"重做"都会撞预算**，必须按区块切片（每个 task 只动一个区块，估算 ≤ 400 行留 100 行缓冲）。这也正是为什么第 1 层值得单独做：它覆盖全部屏幕却只需改 4 个文件。

**其他风险**：

- **零 AndroidX / Java-only 约束**：不得为设计需要引入 ConstraintLayout、Material Components 或 Kotlin（`android/scripts/no-kotlin-check.ps1` 会拦）。新稿里的圆角卡片、阴影、动画在平台控件上需要手工实现。
- **设计稿与生产代码不一致时的口径**：按 `ux-design.md`「生产代码是事实，设计稿是意图」。所以 §2 C 类的 5 处，**按 PRD 走而不是按新稿走**，并且要单独记录偏差，不静默改稿也不静默改代码。
- **`dimens.xml` 是手工维护的，守门脚本不校验间距/字号/字体**（`check_design_tokens.py` 只比对颜色不透明 hex 子集）。改度量没有脚本兜底，靠人工核对 → 建议在第 1 层顺手把字号/圆角的期望值写成一张核对表。

## 5b. 原始建议记录（追溯用；3 件已于 2026-09-22 全部拍板）

### 第 1 件 · 信息架构要不要改（底部标签栏 + 学习库）

- **建议**：**改，但走 PRD 增量正式变更，不要绕过去。**
- **理由**：底部标签栏是这次设计稿"高级简约"观感的主要来源之一，不改就只等于换了套配色，设计稿的核心没进来。而 PRD 是已冻结、已验收的规则，绕过它会让后续每次验收都自相矛盾。
- **代价**：需要先写一份 PRD 增量条；首页的「历史主题列表」要移到学习库，头部「搜索/归档/设置」三个入口的位置随之变化；现工程 `HomeScreen` + `screen_home_body.xml` 要做结构级改动（533 行，必须切 2 个以上 task）。

### 第 2 件 · 字体怎么落地

- **建议**：**正文用系统 `sans-serif`（零成本），品牌字先用 `serif` 族回退，本轮不打包字体。**
- **理由**：Android 中文设备的系统 sans 本身就是 Noto Sans CJK 系，与新稿指定的 Noto Sans SC 观感接近；打包完整 CJK 字体是 5–10MB，只为一个标题字不值得。这样也顺手把「字体未落地」这条历史缺口以最低成本关掉。
- **代价**：品牌字（"知芽 / TREELEARN"）在不同厂商 ROM 上的衬线观感会有差异；要彻底一致就必须打包子集字体（约 +1–3MB）。另外新稿放弃了旧设计系统的楷体身份（霞鹜文楷），这是一次**品牌观感变化**，需要你确认接受。

### 第 3 件 · 是否采用 Harness 流程

- **建议**：**采用。**
- **理由**：这件事横跨「设计 token / 导航结构 / 新增屏幕 / 图标资产 / 多尺寸 / 守门脚本 / PRD 变更」，独立交付项 ≥ 8，且要改 PRD 与多处守门——正好命中 `AGENTS.md` 里"大型改动、多个独立交付项、架构与数据风险"的询问条件。
- **代价**：你要先确认需求与切片，流程比"直接干"多几轮；但 500 行预算已经决定了无论如何都得切片，不采用 Harness 就只能由我手工管切片边界，反而更容易失控。
