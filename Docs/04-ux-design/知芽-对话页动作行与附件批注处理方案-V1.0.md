## 0.1 追加裁决：子分支列表也是图标（2026-09-28 15:03）

**用户第二轮原话**：「分支列表 对应的也是图标，**不要是文字**！」（附截图，红框圈住动作行里的「子分支 1」文字块）

**这是一处我上一轮漏掉的真相**：我按用户 C 裁决的清单保留了 `act_children`，但**没有检查它的形态**——它是四个按钮里**唯一一个纯文字按钮**（`Button` + `layout_width="wrap_content"` + `textSize`，无 drawable），而旁边三个（复制/重新生成/新建分支）都是图标。

**回到原型即可坐实（原型第 1178 行）**：

```jsx
{(kidsByMsg[m.id] || []).length > 0 && (
  <button className="ai-act" title={`子分支列表：这条回答分出了 N 个子分支`}>
    <ITree size={17}/><span className="ai-act-n">{N}</span>
  </button>
)}
```

⇒ 原型画的是 **`ITree` 字形（17px）+ 右上角绿色数量徽标**（`.ai-act-n`：min-width 14px、height 14px、`radius:full`、`background:--green`、白字 9.5px）。**Android 实现把「字形 + 徽标」退化成了纯文本「子分支 N」**——这是本轮要修的偏差。

**落地**：

| 文件 | 改动 |
|---|---|
| `layout/view_answer_actions.xml` | `act_children` 由 `Button`（文字）改为 `FrameLayout`（44dp 热区）+ 内含 `ImageView`（`ic_nav_tree`，24dp，居中）+ `TextView`（`act_children_count`，右上角徽标） |
| `drawable/bg_count_badge.xml` | **新增**：绿色胶囊（`tl_green` 实底 + `space_s2` 圆角），对应原型 `.ai-act-n` |
| `java/.../screen/AnswerActionBar.java` | 字段 `children` 类型 `Button` → `FrameLayout`，新增 `childrenCount`；`render` 内 `setText(子分支 N)` → `childrenCount.setText(String.valueOf(childBranchCount))` |
| `values/strings.xml` | 删 `chat_act_children_count`（「子分支 %1$d」）——徽标只放数字，不再需要整句 |
| 测试 | `ChatMessageRowLayoutTest` 新增 `theChildEntryIsAGlyphWithACountBadgeNotALabel`（断言有字形/有徽标/无 `<Button>`/无 `android:text`/旧串已删）；`IconAssetsTest` 的 `javaDrivenTextualActionsStayTextual` **反转**（原断言「act_children 必须保持文字」已不成立）并新增 `theChildEntryDrawsAGlyphAndItsBadgeUsesTheBrandGreen` |

**为什么不复用 `ic_action_fork`**：fork 是「**新建**分支」这个动作，tree（`ITree`）是「**看**这条回答的分支树」——原型用两个不同字形区分这两个不同意图，Android 侧沿用同一分工。

**未新增 token**：徽标用既有的 `tl_green` + `space_s2`，故 `colors.xml` / `tokens.json` / `design-system/README.md` **均不动**，守门资源数仍 15。

**测试配套**：`ChatMessageRowLayoutTest` 新增 `elementWithBody()` 辅助方法——原有的 `elementAround()` 只取开标签，看不到 `FrameLayout` 里的 ImageView/TextView 子节点，对「元素内部结构」类断言会失灵（这是本次加徽标时才暴露的工具缺口）。

## 0. 结论先行

批注图里一共 **4 处标记**，落到代码上是 **3 个独立改动 + 1 个「保持不动」**：

| # | 批注 | 落在哪 | 判定 | 建议 |
|---|---|---|---|---|
| ① | 动作行「间距变小，现在隔的太开了」 | `view_answer_actions.xml` 每个按钮的 `paddingStart/End=6dp` + `marginStart=space_s1(4dp)` | **真改动** | 按钮内边距 `6dp→0`、`marginStart` `4dp→0`（44dp 热区不动）；窄屏容量另见 §3 拍板项 C |
| ② | 动作行「删除」 | 同上一行，红框圈住的是**整行 4 个按钮** | **需你确认** | 见 §3 拍板项 A（倾向：不是删按钮，是删「多余间距」） |
| ③ | 「附件图标大小减小」 | `screen_chat_body.xml` 的 `chat_attach` pill（图标 **24dp**） | **真改动，根因已坐实** | 图标 24dp → **15dp**，与同排 `model_chip_effort` 一致；热区移到容器 |
| ④ | 输入框上方灰条（无文字标记，但被红框圈出） | `chat_composer_card` 与键盘区的空白 | **疑似** | 见 §3 拍板项 B（本方案**不动**，需你确认它是否也是问题） |

**一句话**：两处都是「元素本身没大问题，是**给它们留的余量太大**」。真正的改法是把 `44dp 触屏热区` 与 `视觉尺寸` 拆开——热区继续保 44dp（无障碍底线），但**视觉盒子收小**。

**两处根因各一句话**：
- 动作行：多余的**不是 44dp 热区，是每个按钮的 6dp×2 内边距**（12dp/按钮），拿掉即从 4.8 字形宽收到 3.1。
- 附件：pill 用了 **24dp** 图标，而同一行的模型 chip 用 **15dp** —— 同一排两个控件的图标档不一致，这是「只有附件显大」的直接原因。

## 2. 实测方法

批注图为 **2x**（正文行距簇 28–29 物理 ≈ 14–14.5 逻辑，符合 2x 手机截图）。量测脚本：

```bash
python artifacts/tmp/gen_annot_evidence.py
# 产出 artifacts/evidence/T-2026-09-28-chat-actionrow-attach-annot-measure.txt
```

关键读数（均为脚本机械输出，非手写）：

| 读点 | 实测（物理） | 换算 | 说明 |
|---|---|---|---|
| 动作行 7 个图标簇中心距 | 134.0–135.0 | **67.0–67.5 逻辑** | 7 簇，含「时间」 |
| 单个图标字形宽 | 26–33 | **13.0–16.5 逻辑** | 对得上原型 17px 字形 |
| 正文行距 | 28–29 | 14.0–14.5 | 定标 2x 用 |
| 附件 pill 外框总高 | 95 | 47.5 | 含红框 |
| 附件 pill 本体列高 | 103 | 51.5 | 单列扫描 |

**关键推论（比例法，与倍率无关）**：字形宽 14.0，中心距 67.5 ⇒ **中心距 = 4.8 个字形宽**。

原型的设计意图是 **44dp 按钮 + 0 间隙**（`gap:0`），即中心距应 ≈ **44dp = 3.1 个字形宽**（字形 ~14dp 时）。

**实测 4.8 个字形宽 vs 意图 3.1 个字形宽 ⇒ 宽出约 54%**。这与你的批注「隔的太开了」完全吻合。

## 3. 拍板项（需要你定）

### A. 动作行红框里那个「删除」，删的是什么？

红框（`y[1357..1531] w=713 物理`）**横跨整行 4 个按钮**（复制/重置/分叉/子分支），不是圈住某一个。两种读法：

- **读法 1（倾向）**：框住的是「这一整行作为**间距问题**的代表」，箭头与「间距变小」指向同一处 → **不是删按钮**，是收间距。
- **读法 2**：这 4 个按钮里有你想去掉的。

**建议：读法 1。**
- **理由**：同一张图上，动作行只被标了「间距变小」与「删除」两个词，且箭头从「间距变小」斜指进红框；若真要删某一个按钮，「删除」的箭头应该指向那个按钮本身，而不是框住整行。此外 2026-09-27 你刚拍板过按钮构成（`view_answer_actions.xml` 头注释第 3–8 行有记录），一天之内再删按钮与那条决定冲突。
- **代价**：若判断错，会保留一个你想删的按钮 —— 反向成本很低（再删一次即可）；而误删一个按钮会破坏已验证的可达性（`act_quote` 等有 44dp 热区断言）。

**请回复：读法 1（只收间距）／读法 2（并指明删哪个）**

### B. 输入框上方那条灰带要不要一起处理？

红框 `y[1599..1631]`（高 33 物理 = 16.5 逻辑）是一条**浅灰横带**，位于草稿框与控件行之间，图上**没有文字批注**。

- **建议：本次不动。**
- **理由**：它是 `chat_composer_card` 的 `paddingTop/Bottom=space_s2(8dp)` 与草稿框 `minHeight=touch_min(44dp)` 共同撑出的呼吸区；现状下它保证了「点哪都能聚焦输入」。在没有明确意图前，把它压扁会让输入区变拥挤，且属于**你上一轮（2026-09-27 composer 改版）刚定稿**的部分。
- **代价**：若你本意是要压这条灰带，本轮不做则下轮要再改一次（成本约 1 行 dimens）。

**请回复：不动／一起压（并说明目标视觉高度）**

## 4. 差异清单（逐项：实测 vs 现值 → 建议 + 理由 + 代价）

### 差异 ① 动作行按钮间距过大 —— 真改动

| 项 | 现值 | 实测 | 判定 |
|---|---|---|---|
| `act_*` 按钮 `layout_width` | `wrap_content`（图标 24dp + 左右各 6dp padding = **36dp**） | 中心距 4.8 字形宽 | 偏大 |
| `act_*` `marginStart`（非首个） | `space_s1` = **4dp** | — | 叠加 |
| 图标 `drawableStart` | `ic_action_*`，`24dp` 矢量 | 字形 13–16.5 逻辑 | 字号合适 |
| 触屏热区高 | `touch_min` = 44dp | — | **保留** |

**现值实际中心距 = 36dp(按钮) + 4dp(margin) = 40dp**；而红框实测比例要求把它压到约 **3.1 字形宽 ≈ 30–32dp**。

**建议**（三选一，其余不变）：

| 方案 | 做法 | 每项中心距 | 与实测比例 |
|---|---|---|---|
| **A（推荐）** | 按钮 `layout_width` 由 `wrap_content` 改 **`@dimen/touch_min`(44dp)** 保持，但 `paddingStart/End` 由 `6dp` 改 **`0dp`**，`drawableStart` 保持 24dp；`marginStart` 由 `space_s1`(4dp) 改 **`0dp`** | **44dp** | 3.1 字形宽 ✅ |
| B | 按钮改 `40dp` 宽，padding `0`，margin `space_s1`(4dp) | 44dp | 同上，但热区掉到 40dp（低于 44dp 底线） |
| C | 保持现值，只把 margin 由 4dp 改 `0dp` | 36dp | 2.6 字形宽，**收得过头**（会挤） |

- **理由**：方案 A 的关键洞察是 —— **当前多余的是 `paddingStart/End=6dp` 这 12dp，不是 44dp 热区**。把 padding 归零后，按钮盒 = 44dp，图标居中，中心距自然 = 44dp = 3.1 字形宽，正好落在实测比例上；同时 44dp 热区（WCAG 2.5.8）**一点不动**。
- **代价**：按钮盒 36→44dp 会让「视觉上更空」，但因为图标居中、`selectableItemBackgroundBorderless` 的涟漪仍以 44dp 画，观感是「图标间距均匀」而非「更宽」。

> ⚠️ 与 2026-09-28 既有决定的关系：`view_answer_actions.xml` 头注释第 10–14 行写着「图标按钮 drop minWidth and pad 6dp so the full worst-case row (7 targets + time) still fits a 360dp column」。**本方案与它冲突**：拿掉 6dp padding 后，7 个 44dp 按钮 = 308dp + 时间，在 360dp 列里**会溢出**。
> ⇒ 因此需要**同时**做一个取舍（见 §5 拍板项 C）：要么接受「时间戳换行/隐藏」，要么把按钮降到 40dp，要么允许横向滚动。**这是本方案唯一真正有代价的地方，必须先定。**

### 差异 ② 附件 pill 高度过大 —— 真改动

| 项 | 现值 | 实测 | 判定 |
|---|---|---|---|
| `chat_attach` `layout_height` | `wrap_content`（内含 **24dp** drawable + 文字 `text_sm`） | pill 本体列高 103 物理 ≈ **51.5 逻辑** | **偏大** |
| 旁边 `chat_model_chip` 的图标 | `model_chip_effort` = **15dp**（`view_model_chip.xml:36-37`），chip 头注释自述「原型约 22px 高」 | `model_chip_effort` = **15dp**（`view_model_chip.xml:36-37`），chip 自述「原型约 22px 高」 | 参照物已成文 |
| pill 的 `drawableStart` | `ic_chat_attach`，**24dp** 矢量 | — | 需降 |

**根因（这是本项最硬的证据）**：同一行里，模型 chip 的图标是 **15dp**、chip 头注释明确写「原型约 22px 高」且「刻意不做触屏靶子，44dp 热区归 `ModelThinkingPicker` 宿主」；而旁边的附件 pill 却塞了一个 **24dp** 图标并自带 padding ⇒ **pill 天然比 chip 高一头**。

**读数对照**：pill 高 47.5–51.5 逻辑 vs 模型 chip 约 22–28dp ⇒ **pill 比 chip 高约 1.8–2.3 倍**。这正是你说的「附件图标大小减小」。

**建议**：

| 落点 | 现值 | 建议值 | 依据 |
|---|---|---|---|
| `ic_chat_attach` 图标 | `24dp` | **`15dp`**（与 `model_chip_effort` 同值） | 同一行的两个图标必须同档；chip 已是 15dp |
| `chat_attach` `drawablePadding` | `space_s1`(4dp) | 保持 4dp | 图标缩小后不用再压 |
| `chat_attach` `paddingStart` | `space_s2`(8dp) | 保持 8dp | — |
| `chat_attach` `paddingEnd` | `space_s3`(12dp) | **`space_s2`(8dp)** | 与 start 对称；当前 end 比 start 大 4dp 是历史遗留 |
| `chat_attach` 触屏热区 | 由 pill 自身撑起 44dp | **移到宿主容器**（同 `ModelThinkingPicker` 的做法） | 视觉 22–28dp、触摸 44dp |

- **理由**：pill 高度由「图标 + 上下 padding」决定。图标由 24dp 降到 **15dp**（= 同排 `model_chip_effort` 的值）后，pill 自然落到 ~22–28dp，与 chip 齐平。**同一行的两个 pill 用同一个图标档，是本项唯一自洽的解法**——这也解释了为什么你单独标了「附件图标」，而不是标「这一行都大了」（chip 本来就合适）。
- **代价**：
  1. `ic_chat_attach` 从 24dp 降到 15dp 是**改共用 drawable**；已核实全仓**只有 `screen_chat_body.xml:370` 一个使用点**，`view_model_chip.xml` 用的是另一个 `ic_think`，⇒ **无副作用**。
  2. pill 变矮后，**触屏热区会掉到 ~22dp**（远低于 44dp）。补救：按 `view_model_chip.xml` 头注释同样的模式，**把 44dp 热区交给宿主容器**，让「视觉 22dp、触摸 44dp」。这一步不做就是无障碍回退（`ChatScreen.java:191` 的 `attachEntry` 绑定与点击逻辑会一起受影响，需同步改造）。
  3. 若 `attachEntry` 当前把点击监听直接挂在 pill 上，改造后要一并迁到容器，属**行为修改**——须按 `.codex/rules/regression.md` 做影响分析。

### 差异 ③ 「间距变小」是否还包含**动作行与正文之间**的间距？—— 已一致

## 5. 待你拍板的第 3 项

### C. 动作行 44dp × 7 在 360dp 列放不下，怎么取舍？

（承接差异 ① 的代价）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **C1（推荐）** | 按钮保持 44dp 热区，**图标视觉 24dp 不变**，但把整行的「子分支计数」按钮在窄屏（<360dp）下省略，时间戳移到第二行 | 全部按钮保留、热区不降 | 窄屏时间戳换行，行高变 +16dp |
| C2 | 按钮降到 **40dp**（热区 40dp） | 一行放得下 | 触屏热区 40dp < WCAG 44dp；仅差 4dp，实际可接受 |
| C3 | 行改横向滚动（`HorizontalScrollView`） | 全保留、不换行 | 引入滚动手势，与「点按」冲突，且要处理边缘渐变 |

- **建议：C2。**
- **理由**：C1 的双行布局改动最大且涉及状态分支；C3 引入手势语义变化；C2 只改一个 dimens 值、且 40dp 仍满足 WCAG 2.5.8 的「至少 24dp」硬要求（44dp 是 Apple/Android 的推荐值，非硬底线）。你当前批注是「间距太开」，40dp 方案既收窄了间距又不用动结构。
- **代价**：真机指纹大的人可能点错相邻按钮；缓解办法是 `paddingStart/End` 只加 2dp（按钮 40dp、间隙 4dp，中心距 44dp）。

## 7. 风险与缺口

1. **批注图不是 2x 手机截图**：宽 1168 逻辑 584，超出 360–412dp 手机列。可能是平板/横向或非 2x。**绝对 dp 不可直接搬**，本方案一律用「字形宽之比」这种与倍率无关的量。**这是本方案最大的不确定性**——若你能确认截图的设备与倍率，可把 §4 的 dp 值钉死。
2. **「删除」的语义未定**（§3 拍板项 A），会改变改动范围。
3. **动作行窄屏溢出是既有矛盾**，不是本次引入；但本方案会把它激化，必须先拍板 C。
4. **附件 pill 热区**：视觉缩到 ~22dp 后若不把热区移到容器，会远低于 44dp 底线 —— 执行时必须带这一步，否则是无障碍回退，且要按 regression 规则做影响分析。
5. **本方案未量测真机当前渲染**：本机 adb 截图缓冲为 3200×2136（旋转存储），且当前前台是另一个应用（`com.knowledgespace.app` / `com.honor.learnwell`），未取到干净的对话页真机图。建议执行前先补一张真机对话页截图，与批注图做同脚本对量。
