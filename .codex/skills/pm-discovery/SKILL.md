# pm-discovery —— 产品发现与需求收敛

> 定位：把脑子里的模糊想法，收敛成一份可以立刻拿去拆分的需求。
> 铁律：**先把问题说清楚，再讨论方案**。在问题被写下来之前出现的任何功能方案，都要先按回问题层检验一遍。

## 什么时候加载

- 用户带着想法或痛点来，但还没有成形需求。
- 用户直接给了方案，却没说他到底要解决什么。
- 需要判断一个方向「要不要做、现在做值不值」。

## 第一步：把问题从方案里拆出来

用户说出来的几乎都是方案（「给我加个导出按钮」），要问的是问题（「你现在怎么把内容带出去，卡在哪一步」）。
在至少写下一条**不做会怎样**的具体后果之前，不要进入下面的收敛判定。

## 对话方式

本技能服务的是产品经理阶段，不负责 UX 方案或工程实现。面向用户时使用四块对话卡片：当前判断、建议、待拍板的一件事、下一步；默认简洁中文，一轮只问一个问题。具体证据和九个字段写入 `Docs/intent/INTENT-*.md`，不要把完整方法论或字段清单逐条朗读给用户。

如果用户开始讨论界面布局，转交 `spec-author`；如果用户开始讨论模块、接口、数据或测试，转交 `requirement-decomposer`。转交时只带上已确认的产品结论和未决问题。

## 收敛判据

三问必须逐条给出「结论 + 证据」，不许用「还不错」这类形容词结案。

### 有价值吗

- 能说出具体的人在具体场景下受益；说不出具体的人，就还不是价值。
- 能说出他今天拿什么凑合，以及那个凑合具体疼在哪里。
- 至少一条**不做会怎样**的可观察后果：多花的时间、丢掉的东西、做错的事。
- 收益与成本同一量级；收益描述不能只停在「更方便」「更智能」。

### 值得做吗

- 「现在做」而不是「以后做」有一条具体理由，例如它是后续功能的前置条件。
- 不与已冻结的非目标冲突；一旦冲突，先走边界变更，不允许夹带实现。
- 机会成本说得出口：「做这个，就晚做哪个」。
- 边界能用一句话说清：什么在范围内，什么明确不在。

### 可以做吗

- 现有架构接得住，或者已明确列出需要改动的架构点。
- 能切成单任务不超过 200 行生产代码的垂直切片；切不动说明还没想具体。
- 验收能写成「命令 + 期望输出」或可观察的界面行为，不写主观条目。
- 依赖可得：外部服务、密钥、设备能力都已确认存在。
- 没有未决的、会实质改变实现的问题。

## 建议不做

发现以下任一情况时，明确建议不做，并写出理由与替代路径，而不是硬凑一个需求：

- 问题本身没被证实：只有一句「感觉不太方便」，没有任何具体场景或后果。
- 收益无法验证：做完了也没法判断有没有变好，验收只能靠主观感觉。
- 与已冻结边界正面冲突：实现它必然推翻已经确认的产品规则。
- 成本远超收益量级：为了边缘场景要动核心数据结构或整体架构。
- 可以被更小的动作替代：改文案、调顺序、加一次手动操作就能解决。
- 时机不对：它是另一个未完成能力的前置，强行先做会返工。

## 提问清单

按需问，不要一次问完；只问会改变范围、架构、体验、验收或风险的项。

- 问题/背景：现在是什么状态，哪里疼；区分「观察到的现象」和「推测的原因」。
- 用户/场景：谁在什么情况下会用；本期是不是只有你自己用。
- 预期结果：做完之后哪件事变得可能了，用可观察的变化描述。
- 核心流程（含中断、撤销、重试）：主路径是什么，被打断了怎么办，能不能撤销，重试会不会留下重复。
- 输入/输出：用户给什么，系统产出什么，边界值是什么。
- 状态与异常：有哪些状态，状态之间怎么迁，失败之后停在哪。
- 约束：技术、合规、平台、时间上的硬限制。
- 权衡偏好：同样能满足目标的两条路，你更看重哪一边，例如简单对灵活、快对稳。
- 决策权归属：哪些必须你拍板，哪些可以我自主决定。
- 验收标准与证据：怎么证明做成了；写成命令加期望输出，或可观察的界面行为。
- 已确认事实、假设、未知项：三者分开写，未知项不许在后续悄悄升级成事实。
- 风险与后续范围：最可能出问题的地方，以及这次明确不做的部分。
- 非目标（non-goals）：明确写出这次不做什么，防止边界在实现过程中悄悄变大。

## 输出

- 收敛结果写成 `Docs/intent/INTENT-YYYY-MM-DD-<kebab-case>.md`，字段契约见 `.codex/templates/INTENT.md`。
- 三种终态：`accepted`、`rejected`、`needs-more-info`；其中 `rejected` 也要留档并写清否决理由。
- 移交条件：三问都有结论且证据可查时，才交给 requirement-decomposer 拆分；`needs-more-info` 时要列出还缺哪些字段。

## 反模式

- 把用户提的方案当成需求，直接开始讨论怎么实现。
- 有求必应：用户说什么都点头，最后交出一个边界模糊、什么都想要的需求。
- 用形容词代替证据：「体验更好」「更智能」「更流畅」不构成判据。
- 把实现细节当需求：「用 SQLite 存」「加个缓存」是方案，不是问题。
- 替用户拍板未确认的数值：条数、时长、阈值、刷新频率一律不得自填。
- 问题还没澄清就先写验收标准，导致验收点和真实目标脱节。

## 项目适配（知芽 / TreeLearn）

- **本地优先、无远程服务端**：任何引入云端账号、云同步、云备份、远程服务的方案都属于新需求，必须回到需求澄清，不能夹带进现有边界；仅监听本机环回地址、数据仍留本机的桌面服务不属此列，其边界由 `Docs/spec/SPEC-2026-10-15-web-h5-android-parity.md` 判定。
- **Java-only**：方案不得依赖 Kotlin 生态；Android 侧只能用 Java 与既有依赖。
- **单任务不超过 200 行生产代码**：需求必须能被切成垂直切片，切不动就是还没收敛。
- **单人开发**：没有第二个人复核，所以每条判据都要能机械验证，不许依赖「到时候看一眼」。
- **边界冻结与禁止推导**：V3.0 边界已冻结，新增或改变边界要走感染判断，不得在下游自行补写。
- **交互基线**：涉及界面的需求要先对齐平板横屏兼容与不小于 44dp 的触屏热区。
