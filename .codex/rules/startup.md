# 启动验证与部署同步

读取时机：生产代码、构建、依赖或启动配置改动前，完成前核对启动证据。仅加载本任务命中的规则；正文约束沿用原适用范围，不因读取而进入 Harness。

## Module startup guard

对 `frontend/`、`backend/` 或 `android/` 下生产代码、构建入口、运行时依赖或启动配置的任何变更，都必须为每个受影响的模块做实际启动检查，之后该变更才能被报告为完整、PASS 或已验证。该 guard 同样适用于直接执行与 Harness 工作。

- 使用模块的正常开发或应用入口，配合有代表性的本地/测试配置。成功的编译、打包、构建、lint、单元测试、mock 上下文或静态配置检查只是补充证据，不能替代进程/应用启动。
- 让进程保持运行直到出现真实的就绪信号：对 web/后端服务，确认框架的 started/ready 日志，并在可用时确认健康端点或首次页面请求；对 Android，在模拟器或设备上启动应用，并确认初始 Activity 正常渲染且无启动崩溃。
- 当多个模块含相关变更时，逐个独立启动与验证。捕获证据后干净地停止临时进程；不要让开发服务器或模拟器无谓地继续运行。
- 验证证据必须记录模块、精确命令或入口、相关环境/profile、就绪信号与关闭结果。不要打印或持久化用于本地启动的密钥。
- 纯文档与纯测试变更可豁免，除非它们变更可执行示例、测试引导或文档化的启动行为。
- 若所需基础设施、凭据、模拟器/设备或其它启动前置条件不可用，把该模块记录为 blocked / 启动未验证，并说明缺失的前置条件。校验器不得从其它测试证据推断启动成功。

## 构建与部署同步

- 修改 `frontend/`、`backend/` 的构建入口、端口、代理、健康检查、环境变量、启动命令或依赖安装方式时，必须检查并同步对应 `Dockerfile`；应用服务增删或端口变更同步 `docker-compose.apps.yml`，数据服务变化同步 `docker-compose.yml`，相关环境变量同步 `.env.example`。
