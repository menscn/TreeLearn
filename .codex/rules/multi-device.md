# 手机与 Pad 的业务共享、展示隔离

## 适用场景

涉及手机/Pad 共性与独有行为、共享业务或状态、展示隔离、窗口自适应、功能开放、跨端数据兼容，以及正式前端/Android 与原型的代码、资源、配置或构建依赖时，在分析、设计、修改和复核前读取。直接执行与 Harness 均适用；本规则不自动创建 Task、不要求整库迁移或给普通 Pad 需求增加无关手机验收。

本文件是多端边界的权威约束；[演进指南](../../Docs/spec/SPEC-2026-10-15-web-h5-android-parity.md)说明当前事实和落地顺序。目标是正式手机和 Pad 共用业务语义、后端契约及正式 Android 宿主，各自演进展示与交互。目标结构不表示手机已接入、自动具备窗口切换能力或已完成双端验证。

## 必须遵守的要求

### 1. 先分类行为，再确定修改位置

在现有方案、PR 或执行记录中，沿入口、生产者、消费者和共享状态分类；不能按目录、请求名称或当前消费者数量判断。一个变更涉及多类时，分别标明范围和证据。

| 分类 | 判定与处理 |
|---|---|
| 共性业务 | 保存、权限、任务语义、错误分类等与展示方式无关的规则，保留一个明确的前端业务决策来源，通过实际调用方验证。当前只有 Pad 消费也可以是共性业务；服务端的安全校验仍独立保留。 |
| 端独有展示 | 列数、间距、面板、导航方式等，仅在指定展示内实现，证明未改变共享默认值、全局样式、状态或副作用。 |
| 端独有功能 | 已确认的产品能力差异，记录适用端、能力入口、业务所有者及不可用时的明确行为；共性领域规则仍复用。先在一端发布不等于永久端独有业务。 |
| 混合变更 | 同时改变共性规则与端展示，分开描述两部分、各自消费者和验证；不能用“只改手机”覆盖共享组件或默认行为的变化。 |
| 待核实 | 无法确认调用方、旧客户端、状态所有权或历史保护时，保留相关路径，核实后再改不确定部分；独立且已明确的部分可以继续。不能静默判为端独有或推断另一端不受影响。 |

业务单一来源不等于把所有业务代码塞入全局 `common/`。是否抽取以及如何降低修改成本，执行[可维护性规则](maintainability.md)；不为第二个空消费者提前抽象，不为复用数量删除不同信任边界的必要校验。

### 2. 按业务领域组织共享模型，隔离展示

以下为随真实业务切片演进的目标，不要求现在新建空目录、批量移动旧文件或复制两套应用：

```text
frontend/src/
  app/                         # 应用初始化、跨领域编排、展示入口选择
  pages/pad/                   # Pad 页面组装
  pages/phone/                 # Phone 页面组装
  widgets/                     # 现有跨区域组合；差异展示同样隔离
  features/<domain>/
    model/                     # 领域用例、业务状态和规则
    ui/shared/                 # 该领域两端语义一致的展示
    ui/pad/                    # Pad 展示与交互状态
    ui/phone/                  # Phone 展示与交互状态
  entities/                    # 业务实体及稳定的实体能力
  shared/                      # 无具体业务决策的 API/平台基础设施和通用 UI
```

- 保持现有 FSD 及 legacy 迁移边界，执行来源为 [ESLint 配置](../../frontend/package.json)。页面/展示消费领域模型，领域模型消费实体和底层接口；`model` 不依赖 Pad/Phone 展示、路由页面、DOM 或窗口宽度。跨领域编排由合适的上层承担，不通过同层互相导入或循环依赖绕开边界。
- Pad/Phone 展示不得相互导入。共用展示提取到含义明确的 `ui/shared`；真正跨领域且不含业务决策的基础组件才进入 `shared`。展示层不得复制保存、权限、任务状态、错误语义等决策。
- 领域模型中的 React Hook 可以负责无展示依赖的订阅/用例适配；弹窗开关、布局测量、焦点与滚动控制留在展示控制层。不能只因文件名为 Hook 或 store 就将其整体视为共性业务。
- 现有混合 store、HTTP/认证流程和旧目录按实际触碰范围逐步分离，保留稳定入口与等价行为断言；不能将现有全部 store/API 文件一次归入共享层而未经调用分析。
- 新增真实多端目录或抽取边界时，在同一变更补齐对应 ESLint/架构检查规则及正反例；现有跨工程门禁通过不代表已经自动检查域内 `model/ui` 依赖。公开入口应明确输入、输出及错误/状态语义，禁止通过深层私有导入绕过约定。

### 3. 明确状态与副作用的生命周期

| 状态或能力 | 所有者与生命周期 |
|---|---|
| 资源、权限、计费、服务端任务结果 | 服务端权威；前端通过统一接口读取或提交命令，不按展示端建立不同事实。 |
| 任务 ID、查询/恢复、幂等提交状态 | 共性用例/会话层维护，独立于某个 Shell 挂载；跨实例语义执行共享状态规则。 |
| 未保存草稿、当前资源、业务选择与逻辑阅读位置 | 由该业务会话维护；需要跨展示保留的状态放在展示切换边界之上，按实际编辑/保存语义恢复。阅读位置使用资源身份及适用的页/段落/锚点表达；像素坐标、缩放和栏内偏移属于布局相关状态，跨布局复用须验证转换或明确回退，不能直接套用旧坐标。 |
| 面板展开、栏宽、浮层、临时焦点 | 对应展示负责，可按约定重建；重建不得顺带清空业务草稿或提交状态。 |
| 相机、文件、登录、分享等平台能力 | 平台接口/正式宿主负责；业务调用能力接口，不以屏幕宽度替代平台可用性或权限判断。 |

- 对订阅、监听、定时器、SSE/轮询、提交、恢复、持久化、取消、重试等逐项说明所有者、启动/释放时机和业务身份。允许多个必要的只读观察者；不能因为两个展示都挂载而重复写入、提交、计费、取消或重试。
- Shell 卸载只清理它拥有的展示资源和观察连接。关闭面板、断开 SSE、窗口切换或取消 UI 请求不自动等于取消服务端任务；取消必须是明确业务命令并沿用现有权限、幂等和终态语义。
- 草稿、在途任务、提交去重和共享 busy 状态不能被旧 Shell 的 cleanup 重置。新旧展示交接要验证失败、快速来回切换、恢复及重复操作，不能仅检查渲染标签改变。
- 本地持久状态也按语义划分：草稿、待同步写入和任务身份沿用账号/租户及资源隔离；栏宽、镜像布局等端专属偏好使用明确的展示作用域，共享设置仍保留单一来源。Phone 初始化不得以默认值覆盖 Pad 偏好，亦不得为隔离展示复制两套业务草稿。触碰 localStorage、IndexedDB 或原生存储的 key/schema 时，明确旧 Pad 数据读取、迁移版本、重复或中断迁移、退出清理及降级处理；未成功迁移前不得清空旧数据，必要用例覆盖已有偏好、未保存/待同步内容和账号切换。
- Shell 上方的内存状态不等于 Activity/WebView 重建或进程恢复所需持久化。按业务已有恢复承诺验证；涉及 appId、origin 或存储位置变更时也核对旧数据可达性，不强制持久化所有临时展示状态。
- 任务和持久状态执行[共享状态规则](shared-state.md)；监听与资源释放执行[资源安全规则](resource-safety.md)。认证退出、用户切换与业务结束所需清理继续按其真实语义执行，不用“保留状态”造成跨用户泄漏。

### 4. 展示隔离覆盖样式、浮层和全局配置

- 展示专用样式使用明确的局部作用域或展示根节点；通用 token、全局 CSS、组件默认参数、全局 UI Provider/配置改变按共性或混合变更评估，检查未修改的调用方。
- Portal、挂到 `body` 的弹窗、独立 iframe/document、原生嵌入页可能离开展示根节点。必须确认样式、语言、主题和布局标识实际传播方式及回收；CSS Modules 或根选择器本身不能证明隔离。允许现有合法的全局弹窗，但其归属和样式继承须明确。
- 滚动锁、键盘/返回键、焦点捕获、选区和系统栏等副作用要在交接或卸载后恢复，并验证浮层仍开着时切换展示、返回及关闭。不能用全局补丁修手机后仅在手机页面验证。
- AI 导学/阅读属于业务模式，Phone/Pad 属于展示维度。遵循[前端双模式规则](frontend.md)，只对实际受影响的组合提供行为证据；未开放的入口记录为未开放，不伪造双端通过。

### 5. 分开决定布局、功能开放、权限和平台能力

- 布局选择由应用入口集中管理，以可用窗口为依据；新增自适应时明确断点、初次选择、窗口变化、输入法/低高度及状态交接策略。不得在业务模型散落 `isPhone`/宽度判断，不把物理设备名称当作全部窗口情境。
- 功能是否在某展示开放、用户是否有权限、设备是否具备原生能力是独立判断。隐藏按钮不能代替服务端授权；手机功能先开放也不能改变同资源在 Pad 上的合法性或数据语义。
- 当前正式 Pad 行为是治理与普通修改的回归基线；获明确授权的自适应需求可以调整设备准入、方向和可调整窗口配置，需列明预期变化及继续保留的 Pad 功能。不得把现有横屏/设备限制永久固化，也不得借本规则提前修改它们。
- 正式产品共用正式 Android 宿主和资源链路，保留其认证、桥接、隐私、分享、更新等能力。一套宿主不要求合并所有辅助 Activity；修改按[Android 规则](android.md)和[契约规则](contracts.md)验证。
- 功能开放开关的默认值、来源、失效行为和恢复入口在实际实现时定义并验证。环境/构建路由不自动等于按 Shell 的功能开关，不假定项目已存在统一远程开关服务，也不因本规则新增此类服务。
- 一端尚未支持某功能时，从资源/通知/链接进入要有明确降级与返回；保留已产生任务的查询/恢复能力，不能把合法资源误判为不存在或清掉业务状态。

### 6. 共用 API 同时保护数据与发布兼容

- 同一业务复用统一 Java `/api` 契约、身份和资源语义；前端继续使用统一客户端，不直接调用 Core，不为 Pad/Phone 复制同义业务接口。展示专属数据组合有真实需求时按现有契约规则设计，不以终端名称替代领域边界。
- 兼容验证覆盖接口、持久数据与业务状态：新客户端写入后，支持范围内的旧 Pad 能读取、编辑和保存；旧端写入后，新端也能正确消费。新增可选字段不自动保证枚举、内容格式、默认值、错误分类、时间单位、任务终态和重试语义兼容。
- 同账号跨设备并发不等于窗口内切换。涉及可共同编辑/删除或离线回放的业务时，Phone 必须继承现有 revision/CAS、幂等与冲突处理协议；按实际链路验证 Pad/Phone 同时编辑、删除后的离线回放、旧请求晚到及重复重试，不能静默覆盖较新内容、复活已删除资源或重复创建副本/计费。没有通用同步需求时不另建同步平台，也不将所有业务强制改为同一冲突策略。
- 涉及独立发布客户端时，明确支持的 APK/前端版本集合及证据；涉及服务滚动发布时，核对 Java/Core/worker 新旧混部、已有数据和在途任务。通常先发布兼容服务，再开放新入口，最后在真实消费者与恢复路径已核实后退役旧路径。
- 统一 APK 发布若影响最低支持版本或强制更新，必须评审实际更新策略和旧 Pad 用户的升级影响；不能因改动只在 Phone 展示而跳过更新策略。治理规则自身不更改现行策略或宣称线上已启用强更。
- 关闭功能入口或回退 APK 不会自动撤回已写内容格式、任务、计费或状态迁移。发布记录应给出受影响数据的兼容、恢复/补偿办法及验证；没有证据不得写“可回滚”。
- 本节只定义多端补充检查；API/桥接/错误/认证的权威要求与独立复核见[契约规则](contracts.md)，数据及发布责任见[协作规则](collaboration.md)，文档证据见[文档一致性规则](documentation.md)。

### 7. 正式产品与原型保持隔离

- 正式 `frontend/` 与根 `android/` 是正式产品链路；`mobile-prototype/` 保持独立演示工程。正式运行时不得导入原型的源代码、受控镜像、本地 adapter、Mock/样例、PDF stub、原型资源或 Android 宿主；原型运行时不得直接依赖正式工程源代码或产物。
- 原型内部已授权的 `formal-mirror/`、适配器和 stub 可以保持既有依赖；镜像是受控快照，不是共享 SDK，也不是一次性复制到正式产品的迁移来源。未来接入从已确认交互和正式能力逐片实现，明确任何复用的来源、所有权与历史保护。
- 相对路径、别名、类型导入、动态导入、CSS/HTML 资源、local package、符号链接和构建资源声明都属于依赖边界。维护/测试工具可以按明确职责检查两套工程，但不能被生产代码作为转接路径绕过隔离。
- 静态依赖检查只证明已覆盖的声明引用，不证明没有复制业务规则、资源许可正确或运行时绝无影响。复制/粘贴、外部脚本和未覆盖的构建/运行时行为仍须按来源及实际链路复核。

### 8. 按真实业务切片演进并交付证据

1. 记录当前 HEAD、实际工作区及相关入口/配置，分清并发改动；追踪受影响行为的历史保护，遵循[防回归规则](regression.md)。
2. 分类行为，列出修改与保留项、实际调用者、状态所有权及端差异；未核实部分明确缺口。
3. 只对本次触碰的领域建立需要的边界。先让既有 Pad 入口消费同一业务实现并保留原行为，再由获授权的 Phone 切片接入；避免同时搬目录、改语义和改布局而无法定位回归。
4. 每个切片以实际生产入口、模型调用、开放能力和测试证明完成。仅创建目录、修改文档或让新入口继续走 Mock 不构成正式接入。
5. 第一个双展示切片就验证窗口切换及状态生命周期，不等整个手机产品完成才补；分别验证该切片的共性业务、两端独有行为和最相关的失败场景。
6. 按实际影响执行既有 lint、测试、浏览器/设备、启动、原生及契约检查；[遥测规则](observability.md)要求的日志和事件覆盖沿用现有体系，禁止增加敏感业务内容。
7. 核对支持版本、上线顺序和恢复安排；旧路径仅在真实消费者、兼容版本、在途任务和保护迁移证据成立后退役。
8. 同步当前文档和既有文档影响记录，复核最终 diff 与授权范围。已知错误为 FAIL，缺少必要行为证据为 PARTIAL；源码检查或构建不能替代双端交互验证。

## 原理

目录表达所有权，依赖方向限制耦合，状态生命周期决定两套展示能否安全交接。只有目录拆分而仍复制业务决策、共用未受控全局副作用或将任务绑定页面，会继续造成同步漏改和端间回归。业务共享也不意味着每个端必须同时开放所有能力；稳定的业务语义、明确的能力入口和各自展示可以独立演进。

单一 APK 统一发布，并不消除旧 APK、服务滚动发布和已经持久化的数据。跨版本“能请求成功”与“能正确继续编辑/恢复”必须分别验证。自动门禁负责可机械判定的引用与路由，语义、设备交互及复制来源依然需要对应证据。

## 正反例

| 场景 | 正确处理 | 不足或错误的处理 |
|---|---|---|
| 只有 Pad 使用的保存规则修复 | 按语义归为共性，定位权威业务实现和实际 Pad 消费者；未来 Phone 复用 | 因只有一个消费者复制成 Pad 专用保存，以后再维护一份 Phone 保存 |
| Pad 栏宽调整 | 在 Pad 展示内修改，检查全局样式与浮层影响，验证相关 Pad 入口 | 修改全局默认宽度后以文件位于 Pad 目录声称手机不受影响 |
| Phone 先开放 AI 入口 | 区分发布节奏与永久产品差异，复用任务/权限/错误规则，明确未开放入口的返回 | 新建 Phone 任务语义，或认为隐藏 Pad 按钮就不会影响 Pad 数据 |
| 共用组件默认值修改 | 标为共性/混合，检查所有实际调用方及显式覆盖值 | 只测试提出需求的一端 |
| 草稿未保存时折叠/展开窗口 | 保持业务会话与草稿，交接展示并释放自身监听 | 旧 Shell cleanup 清空 store，或两个展示同时提交 |
| Phone 首次启动或布局变化 | 保留 Pad 本地偏好与待同步内容，阅读位置按逻辑锚点恢复或验证坐标转换 | 用 Phone 默认值覆盖共享 key，或把 Pad 像素偏移直接用于 Phone |
| 新内容格式写入 | 验证支持的旧 Pad 读取、编辑保存与新端消费旧数据 | 仅验证新字段可省略或 HTTP 200 |
| 两设备编辑同一笔记 | 继承版本与幂等协议，验证冲突、离线回放和晚到请求 | 只验证分别保存成功，把同时写入造成的覆盖当作正常同步 |
| 发布包含 Phone 功能的统一 APK | 核对实际最低版本/强更策略和旧 Pad 用户影响 | 因 Phone 独有 UI 就跳过 APK 更新策略评审 |
| 原型引用与测试 | 原型内部镜像/adapter 保持隔离；正式接入验证真实入口和后端 | 通过原型 LegacyApp 测试、修改后端 URL 即宣称正式 Phone 可用 |
| 无法确定后台任务消费者 | 保留兼容路径，核实支持版本和在途任务；继续无关确定部分 | 仓库搜索不到就删除，或暂停所有无关 Pad 开发 |

## 验证入口

- 在仓库根运行 `node scripts/ci/check-multi-device-boundaries.mjs`，回归运行 `node --test scripts/ci/check-multi-device-boundaries.test.mjs`。使用锁定的现有前端依赖；不得为通过检查新增依赖、全局忽略、宽泛白名单或自动历史基线。
- 检查器负责声明的源依赖和明确配置引用；被选中时扫描完整受管输入，不能只扫 changed files 而漏掉指向已删除/改别名目标的旧导入。支持范围、必需输入与未覆盖形式须由检查器诊断及[演进指南](../../Docs/spec/SPEC-2026-10-15-web-h5-android-parity.md)说明。退出码 `0` 表示覆盖范围内通过，`1` 表示边界违规，`2` 表示无法验证；未支持的相关语法、缺少必需输入或环境不完整不能按通过处理。
- 缺少必需源文件/入口必须失败；干净 checkout 中尚未生成的 `dist`、Capacitor 产物等只有在明确识别为输出声明时才可规范化目标并检查边界，不能用生成目录例外放过缺失导入。
- CI 通过独立 `architecture` 范围和作业接入总门禁；选中后跳过、失败、取消或范围判定失败都不能使总门禁成功。规则/指南修改保持轻量检查，不因此触发所有业务模块构建；原有模块和文档门禁继续独立执行。
- 规则自身修改复核上表分类、状态和兼容场景，以及[文档门禁](documentation.md)要求的 diff、UTF-8、链接和旧表述反向检索。行为修改按实际入口追加共性/各端/窗口/旧版本证据；尚未落地的 Phone 不填写虚假的设备 PASS。
