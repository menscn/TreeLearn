# 可维护性与修改成本增量治理

读取时机：新增或修改人工维护的生产代码、重构、拆分，触碰大文件、高复杂度文件及函数，或涉及热点治理、模块职责调整、共享业务规则、状态边界或兼容分支退役的分析、设计及完成复核前。直接执行与 Harness 工作均适用；正文约束不因读取而要求进入 Harness。

## 治理目标与默认阈值

- 行数和复杂度是风险信号，不是机械拆分指令。治理目标是让业务流程更容易理解、修改和验证，把下一次同类需求的修改成本纳入收益判断，并在保持业务阅读流畅、职责内聚和状态可追踪的前提下逐步降低复杂度。
- 默认硬门禁为：文件 800 有效行、普通函数或方法 150 有效行、圈复杂度 20、控制流嵌套 4 层。有效行不含空行和纯注释行；存在可靠的现有 lint 或分析器时，以其口径为准。
- 共享 TypeScript 检查器可靠识别的 React 函数组件，150 有效行仅作为警告阈值：新增超限或历史超限后继续增长均告警，不阻断 CI，也不要求为组件行数增长单独申请批准。识别要求组件名称以大写开头或为默认导出，且自身返回 JSX；支持从 React 导入的 `memo`、`forwardRef` 包装。无法可靠识别时按普通函数检查，具体支持范围见[检查器说明](../skills/line-budget/SKILL.md)。组件内部的普通函数、事件处理函数和 Hook 回调仍独立执行 150 行硬门禁；所在文件、圈复杂度和嵌套仍执行原硬门禁，统计口径不变。
- 技术栈、目录或特定入口已有更严格门禁时，始终采用更严格值，不得用本规则放宽。例如 `frontend` 继续执行其现有文件、函数、复杂度、嵌套和应用壳上限。
- 数值上限默认适用于人工维护的生产源码。测试、生成文件、锁文件、第三方代码、静态数据和迁移文件不纳入统一数值门禁，但仍须保持合理组织，不得用这些位置隐藏生产业务逻辑。

## 增量棘轮

- 未触碰的历史超限代码不要求在无关任务中顺手治理。修改前识别并记录本次实际触碰的超限文件、函数或方法及其适用指标；修改后记录同口径结果。
- 低于硬门禁上限的现有代码可以在保持内聚和可读性的前提下正常演进，但不得借此创建新的硬门禁超限。React 组件行数沿用相同增量比较方式，仅将新增超限和继续增长降为警告；历史超限不变或下降不新增警告。
- 已超出硬门禁的文件、函数或方法，其已超限指标原则上不得比修改前增长；安全可行时应随本次变更下降。新增业务职责默认放入边界清晰的独立模块，热点文件保留稳定入口、必要编排和关键业务决策。
- 不得通过移动无关代码、改变统计口径、增加忽略项或把业务逻辑转移到豁免文件来制造指标下降。
- 若没有机械化工具，使用可复核的前后行数、符号范围和控制流审查；不得把无法可靠测量的指标虚报为精确 PASS。本规则本身不授权新增依赖或扩大任务范围建设质量工具。

## 拆分与阅读流畅性

- 抽取必须先证明不会损害主流程的阅读流畅性、内聚性和状态可追踪性，并至少满足一项：能够命名为独立且完整的业务职责；具有清晰、相对稳定的输入输出或状态边界；能够独立测试或显著减少主流程中的分支、状态和副作用；确有合理复用价值且不会引入不当耦合。仅仅能够移动代码或减少行数不构成抽取理由。
- 主流程应能够按业务顺序自上而下阅读。抽取后的模块名称必须表达业务意图，入口文件保留理解流程所需的关键顺序、决策和异常路径。
- 禁止把连续且高度内聚的流程切成大量微小文件或仅调用一次的无意义包装层；禁止创建职责含糊的 `utils`、`helper`、`common` 代码堆放点。
- 禁止为减少行数而复制逻辑、转移复杂条件、隐藏共享状态、增加循环依赖，或让错误处理、事务边界、状态变更和时序散落到难以追踪的位置。
- 如果拆分会导致理解普通业务路径时频繁跨文件跳转、破坏流程连续性或显著增加间接层，应保持当前职责边界，优先做局部简化、减少嵌套、改善命名或提炼真正独立的纯逻辑，并保证硬门禁指标满足增量棘轮。组件行数警告用于提示评审，不强制机械拆分。
- 设计与评审按以下顺序权衡：业务语义和行为正确；主流程流畅、职责内聚、状态可追踪；复杂度和嵌套降低；文件和函数行数降低。后项不得以牺牲前项为代价。

## 修改成本与热点治理

### 适用场景

- 随本次改动沿实际业务链路选择少数相关热点，结合 Git 变更与共同修改、重复回归、实际消费者及影响范围说明依据；优先关注经常修改、经常出错或影响范围大的流程。热点可以是业务流程、共享规则或状态路径，不要求文件超限，不建立长期热点台账或统一评分。
- 本次识别的热点，以及模块拆分、职责调整、共享业务规则的实现变更、状态边界调整和兼容分支退役，必须执行下述成本评估。普通局部修改沿用既有简短影响分析；未触碰的历史热点不要求在无关需求中治理。

### 必须遵守的要求

在现有方案、PR 或执行记录中回答四问，不适用项简注理由。直接执行与 Harness 使用相同要求；不新增报告、Task、独立答题流程或例行审批。

| 评审问题 | 可复核的证据 |
|---|---|
| 同类需求需要同步改多少处？ | 选择一个与本次目标相关的代表性需求，列出必须同步修改的业务决策点、路径及职责；治理前后使用相同需求、入口和比较基点，区分业务决策与必要的协议映射，不以整个 diff 的文件数代替。 |
| 同一业务规则有几份实现？ | 指明权威实现、重复判断和必要的跨端校验，说明各自职责、消费者及一致性验证；不能仅凭代码相似就合并不同信任边界的校验。 |
| 追踪一个状态需要跳转哪些位置？ | 指明状态的权威来源、写入入口、派生状态及关键失败和恢复路径；沿具体路径核对所有权与隐式依赖，跳转数量只用于定位理解成本。 |
| 兼容分支还有真实消费者吗？ | 核对实际调用方、支持版本及保留或退出条件；涉及独立发布客户端、旧任务或回滚路径时检查对应证据。仓库内搜索无结果不足以证明可以删除，消费者未核实前保留兼容路径。 |

- 优先减少重复事实、隐式状态和不必要的同步修改。必要的跨模块协作、跨端校验与版本兼容可以保留，但必须说明职责、必要性及验证方式；收敛逻辑仍须遵守既有依赖边界、状态所有权和安全约束，不能把业务决策随意堆入公共模块。
- 评估必做，治理按需。普通业务需求触碰热点时说明成本变化与取舍，可以记录暂缓治理的具体理由，不强制扩大重构范围。专门的治理改动必须证明至少一项具体收益，例如减少同一规则的同步决策点、明确状态所有权或消除不必要的流程跳转；仅有行数下降不足以证明收益。

### 原理

同一事实由多个位置独立决定、状态依赖藏在调用顺序中，会增加遗漏同步、错误恢复和回归验证的成本。文件变短只是一个信号；修改点和跳转数量用于诊断，不设置统一数量上限，也不汇总成总分。收益应体现在同类需求更容易理解、修改和验证，并由明确的职责、数据流与行为证据支持。

### 正反例

以下是假设场景，用于解释前述要求，不声明项目当前实现或独立新增门禁；满足成本要求仍须通过其他适用检查。

| 场景 | 证据与判定 |
|---|---|
| 重复决策收敛 | 同一规则的三份独立判断收敛到一个权威决策；同类需求演练证明只需修改该决策，相关入口保留等价行为断言，可以作为具体治理收益。 |
| 机械搬行 | 主文件变短，但决策、状态写入和异常处理散落到更多包装层，实际流程更难追踪，判定 FAIL。 |
| 必要跨端校验 | 前端输入提示与后端权限校验职责明确，信任边界及一致性验证可核实，满足成本要求；不为追求一份代码而删除必要校验。 |
| 兼容消费者未核实 | 只有仓库搜索无结果，缺少支持版本、外部消费者或相关旧任务的核验，退役验证为 PARTIAL，保留兼容路径；已知会破坏消费者仍删除则为 FAIL。 |
| 热点业务改动暂缓治理 | 完成四问，说明本次仅做必要业务修改和暂缓理由，仍满足原有棘轮与行为验证，可以完成业务需求；不能声称已经产生治理收益。 |

### 验证入口

- 治理前后对相同代表性需求或状态路径做演练，记录实际决策点、权威实现、状态路径和消费者的代码依据，说明至少一项成本来源如何减少；推测节省的时间或单纯的文件计数不能替代证据。
- 按[防回归规则](regression.md)复用有效的行为测试或可复现操作，保留等价行为断言并验证相关失败、恢复或兼容场景。源码对照只能证明结构与调用关系，不能代替必要的行为验证。
- 既有前端依赖边界、Python import-linter 和各栈数值门禁独立验证，不能用成本收益抵消硬门禁失败，也不能仅凭数值门禁通过推断治理收益。完成判定见下节。
- 仅修改治理规则时，用上述五类场景复核适用范围、证据和判定，并执行[文档一致性门禁](documentation.md)；不为规则改动新增无关业务测试、构建或启动要求。

## 例外与完成证据

- 原子缺陷修复、安全修复、兼容入口、框架强制入口或高度内聚流程确实不适合拆分时，可以保留在原位置；必须记录不拆分理由、评估过的方案、回归风险和验证证据。
- 批准例外、保留兼容和暂缓治理在现有记录中注明负责人、退出条件及再次复核触发点；默认在再次触碰或相关发布时核验。按[协作规则](collaboration.md)执行，不另建台账，不改变已有事前批准条件。
- 若任何已超限的硬门禁指标需要继续增长，必须在实现前获得用户明确批准，并记录增长范围、必要性和替代验证。禁止事后补批；未获批准不得报告完成或 PASS。React 组件行数警告不适用此批准要求。
- 纯结构拆分必须保持外部 API、业务语义、状态顺序、异常处理和用户行为不变，并按照[防回归规则](regression.md)保留等价行为断言。
- 完成记录按实际命中范围包含：被触碰的数值超限文件或函数及前后指标；抽取出的业务职责或选择不拆分的内聚性理由；对主流程、状态边界、错误处理和调用链可读性的复核；命中的成本评估、治理收益证据或普通业务改动暂缓治理的理由；相关 lint、测试、构建和行为回归证据。
- 以下情况必须判定为 FAIL：机械搬行或无意义包装；新增不必要的重复事实、隐式状态或流程碎片化；拆分后业务流程更碎片化或状态更难追踪；未经批准使历史超限硬门禁指标继续恶化。数值门禁通过不能抵消这些问题。
- 缺少必要的前后指标、成本评估或治理收益验证时判定为 PARTIAL，不得宣称完成或满足棘轮。普通业务改动已完成评估并说明暂缓治理理由，不因没有治理收益而判定未完成；仅有组件行数警告不构成失败。
